Technical Design Document: PLM Production Support Agent

Companion to: PLM_Production_Support_Agent_PRD.md Orchestration Framework: Google Agent Development Kit (ADK), consistent with the existing internal data agent Target Platform: Google Cloud Platform

1. Architecture Overview

The agent is a backend-orchestrated conversational service embedded as a chat panel inside the PLM application. It uses an ADK-based root agent that routes each user turn to one of three capability paths: knowledge retrieval (RAG over Confluence), structured status lookup (season-style API), or ServiceNow ticket operations (MCP-based tool calls). A confidence-gating layer sits between the knowledge path and the user, ensuring low-confidence answers fall back to ticket creation instead of being presented as fact.

2. Component Breakdown

2.1 Client Layer

  • Embedded Chat Panel: Lightweight chat UI rendered inside the existing PLM application shell. Communicates with the agent backend over HTTPS. No direct ServiceNow or Confluence access from the client.

2.2 Edge / Access Layer

  • HTTPS Load Balancer: Single entry point for the agent service; terminates TLS.
  • Identity-Aware Proxy (IAP): Enforces that only authenticated Nike users can reach the Cloud Run service.
  • Okta Federation: Existing Okta SSO federated via Workforce Identity Federation, so the agent inherits the same identity and permission model as the PLM application itself. User identity flows through to every downstream call (status API, ServiceNow) for permission scoping.

2.3 Agent Service (Cloud Run)

  • FastAPI Endpoint: Stateless HTTP entry point handling chat turns, session ID management, and streaming responses back to the client.
  • ADK Root Agent / Orchestrator: Owns the conversation loop, session/memory state, and decides which tool(s) to invoke per turn.
  • Intent + Domain Classifier: A lightweight, cheaper-model classification step (e.g., a smaller Gemini model) that tags each query with a domain (costing, BOM, line planning, library, platform/technical) before routing. This mapping also drives ServiceNow assignment group selection.
  • Confidence Gate: Evaluates retrieval/answer confidence from the knowledge tool. Below threshold → triggers ticket-creation flow instead of returning an answer. This is the concrete mechanism behind the PRD's "never hallucinate" requirement.

2.4 ADK Tools

  • Knowledge Retrieval Tool: Wraps a query against Vertex AI Vector Search, returns top-k passages plus a groundedness/confidence score, and generates the final answer with source citations.
  • Status Lookup Tool: Wraps the existing season-style status API call; passes through the authenticated user's identity for permission-scoped results.
  • ServiceNow Tool: Wraps ServiceNow MCP server calls (create, read, update, cancel, list/search tickets). Includes a summarization step that converts conversation context into a clean, technical-only summary before it's ever sent to ServiceNow (SOX requirement from the PRD).

2.5 Data / Knowledge Layer

  • Confluence Ingestion Pipeline: Scheduled or webhook-triggered job that pulls updated Confluence pages, chunks them, and re-embeds changed content only (incremental indexing) rather than a full reload each time.
  • Vertex AI Embeddings + Vector Search: Stores the embedded knowledge base; queried by the Knowledge Retrieval Tool at conversation time.

2.6 External Systems

  • PLM Season-Style Status API: Existing internal API, called directly — no direct database access.
  • ServiceNow MCP Server: Preferred integration path (GA in 2026); exposes ServiceNow tables/actions as callable tools. REST Table API is the documented fallback if the Nike instance doesn't yet support it.

2.7 Observability and Governance

  • Cloud Logging / Audit Trail: Every tool call (especially ServiceNow create/update/cancel) logged with a link back to the originating conversation ID, satisfying the PRD's audit requirement.
  • Cloud Monitoring + Dashboard: Tracks deflection rate, routing accuracy, latency, error rate, and cost per conversation.
  • Secret Manager: Holds ServiceNow service account credentials and any other integration secrets.
  • Evaluation Harness: RAGAS-style regression suite run pre-deployment and on a recurring schedule against production traffic samples.

3. Data Flow (Primary Conversation Turn)

  1. User sends a message from the embedded chat panel.
  2. Request passes through the load balancer, IAP, and Okta-based identity check.
  3. FastAPI endpoint receives the request with the authenticated user context and session ID.
  4. ADK root agent loads session state/history and passes the query to the intent/domain classifier.
  5. Based on classification, the orchestrator selects a tool path: - Knowledge path: Knowledge Retrieval Tool queries Vector Search → confidence gate evaluates the result → if confident, answer is returned with citations; if not, falls through to ticket creation. - Status path: Status Lookup Tool calls the season-style API with the user's identity → result formatted conversationally. - Ticket path: ServiceNow Tool generates a clean technical summary → calls the MCP server to create/update/cancel/list a ticket → returns ticket number/status to the user.
  6. Response streamed back to the client; all tool invocations logged for audit.

4. Security and Compliance Notes

  • All downstream calls (status API, ServiceNow) are scoped to the authenticated user's own permissions — the agent does not have a standing "super user" identity for data access.
  • ServiceNow tool is constrained so a user can only update or cancel their own tickets, never arbitrary ticket numbers (per the prompt-injection/abuse mitigation identified in the PRD).
  • Conversation content sent to ServiceNow is always a generated technical summary, never raw transcript text, to satisfy SOX.
  • Secrets (ServiceNow service account, API keys) live in Secret Manager, never in code or environment files.

5. Phased Implementation Plan

Phase 1: Foundation — Knowledge and Status (MVP)

  • Stand up Cloud Run service, FastAPI skeleton, ADK root agent with a single tool: Knowledge Retrieval.
  • Build the Confluence ingestion pipeline (initial full load) and Vertex AI Vector Search index.
  • Implement the confidence gate (initially can just message "I'm not confident, would you like me to create a ticket?" without live ServiceNow integration yet).
  • Integrate the Status Lookup Tool against the season-style API.
  • Basic Okta/IAP authentication wired end-to-end.
  • Exit criteria: Agent answers how-to and status questions accurately in a dev/staging environment; eval harness passes baseline accuracy targets.

Phase 2: Core ServiceNow Integration

  • Integrate ServiceNow MCP server (or REST fallback) for ticket creation only, with intent-based assignment group routing.
  • Build the clean-summary generation step for SOX compliance.
  • Return ticket numbers to users; log every creation for audit.
  • Exit criteria: Agent reliably creates correctly-routed tickets from real unresolved conversations in staging.

Phase 3: Full Ticket Lifecycle and Production Hardening

  • Add ServiceNow read/update/cancel/list-search capabilities.
  • Implement rate limiting, retry/backoff for downstream calls, and graceful degradation messaging.
  • Build the admin/observability dashboard (deflection rate, routing accuracy, latency, cost).
  • Define and instrument SLA targets.
  • Formalize data retention/purge policy for logs.
  • Exit criteria: Agent passes a production-readiness review against the PRD's non-functional requirements.

Phase 4: Scaled Production Rollout

  • Promote through dev → staging → prod with CI/CD and the eval suite as a regression gate.
  • Roll out to a limited user group first, monitor dashboard metrics, then expand PLM-wide.
  • Assign ongoing knowledge base content ownership within the support/product team.
  • Exit criteria: Stable operation at full user load, meeting defined SLA and cost targets.

Phase 5: Version Two Enhancements

  • Jira integration to surface linked tickets against ServiceNow incidents.
  • Proactive status-change notifications.
  • Feedback loop (thumbs up/down) feeding back into knowledge base gap analysis and the eval suite.
  • Exit criteria: Each v2 feature independently evaluated and rolled out without regressing core v1 functionality.

6. Open Technical Questions

  • Exact model choice for the intent classifier vs. the answer-generation model (cost/latency tradeoff).
  • Whether Vector Search or a lighter-weight alternative is justified at current knowledge base size.
  • Specific numeric confidence threshold and how it's calibrated against the eval harness.
  • Whether session state is held in-memory per Cloud Run instance or externalized (e.g., Firestore/Memorystore) for multi-instance consistency.
  • Final MCP vs. REST decision, pending confirmation of the Nike ServiceNow instance version.
