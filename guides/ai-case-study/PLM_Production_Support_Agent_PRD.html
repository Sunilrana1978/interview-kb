Product Requirement Document: PLM Production Support Agent

1. Overview

Product Name: PLM Production Support Agent (working title)

Purpose: A production-grade, embedded conversational AI agent within the PLM (Product Lifecycle Management) application that helps end users resolve functional and process questions in real time. When the agent cannot confidently resolve an issue, it creates a ServiceNow ticket automatically, routes it to the correct assignment group based on the identified intent/domain, and gives the user the ticket number. Users can later return and ask the agent for status updates, request updates, or cancel tickets — all conversationally.

Primary Goal: Reduce time-to-resolution for PLM users, deflect low-complexity support tickets through grounded self-service knowledge, eliminate hallucinated answers by falling back to a governed ServiceNow ticketing workflow with correct team routing, and operate as a reliable, secure, observable production system — not a proof of concept.

2. Background and Problem Statement

The PLM application supports the end-to-end product creation lifecycle — from concept and inception through phases such as season/style alignment, costing, BOM (Bill of Materials) management, line planning, and library/master data management. Each phase involves different personas, workflows, and specialized modules.

Today, when users hit a process question ("where is my style in the workflow") or a functional question ("how do I add a BOM line item"), they either: - Search Confluence documentation (not optimized for natural-language search), - Ask peers or team leads (not scalable), - Manually log into ServiceNow and create a ticket themselves — choosing subject, detail, and assignment group on their own, which frequently causes misrouting and delay.

There is no single, intelligent entry point that understands PLM domain context, module-specific terminology, and can act on behalf of the user when a real issue needs to be escalated.

3. Goals and Success Metrics

Goals: 1. Provide accurate, grounded answers to "how do I" and functional questions using the Confluence-based knowledge base — never hallucinate. 2. Answer process and status questions using the existing season-style status API. 3. When the agent cannot resolve the issue, automatically create a ServiceNow ticket with the correct assignment group based on detected intent, without the user ever touching the ServiceNow UI. 4. Support full ticket lifecycle management conversationally: create, read/status-check, update, cancel, and list/search. 5. Operate as a secure, observable, resilient production system.

Success Metrics (illustrative — to refine with stakeholders): - Self-service deflection rate (percentage of queries resolved without a ticket). - Ticket routing accuracy (percentage correctly assigned to the right group on first pass). - Average time to ticket creation compared to manual submission. - User satisfaction / thumbs-up-thumbs-down feedback rate on agent answers. - Reduction in "wrong queue" reassignments in ServiceNow. - System uptime and graceful-degradation incident count.

4. Users and Personas

  • PLM End Users: Designers, developers, planners, and merchandisers using functional modules like costing, BOM, line planning, and library management.
  • Support and Operations Teams: Domain-specific ServiceNow assignment groups such as Costing Support, BOM Support, Line Planning Support, Library/Master Data Support, and general PLM Platform Support.
  • PLM Product and Engineering Team: Own the knowledge base content and agent behavior, and monitor ticket deflection and routing accuracy.

5. Scope

In Scope for Version One: - Conversational interface embedded inside the PLM application. - Retrieval-augmented answering grounded in the Confluence-based knowledge base (manuals, FAQs, module-wise and domain-specific documentation), ingested and synced into a dedicated vector store/search index rather than queried live. - Intent/domain classification mapped to ServiceNow assignment groups via a configurable lookup table (costing, BOM, line planning, library/master data, general navigation, platform/technical). - Process/status lookups via the existing season-style status API, which returns current program cycle stage (e.g., initial phase, season partner alignment, confirmation) and pending items — no direct database access required. - Full ServiceNow ticket lifecycle management: create, read/status-check, update, cancel — via ServiceNow's official MCP server (preferred, GA in 2026) or REST Table API (fallback) — fully invisible to the user. - Ticket list/search: view recent tickets by time range (e.g., last 30 days) or look up a specific ticket by number. - Ticket content sent as a clean, technical-only summary generated by the agent — never raw conversation text — to satisfy SOX compliance. - Fallback-to-ticket logic when confidence is low, instead of guessing.

Version Two Candidate Features (documented now, planned for later implementation): - Jira Integration: Surface linked Jira tickets against a ServiceNow incident/request, giving users visibility from initial report through engineering-level resolution. - Proactive Status Notifications: Notify users when their ticket status changes, without requiring them to ask. - Feedback Loop: Thumbs up/down (or similar) rating on agent answers to continuously improve knowledge base quality and identify content gaps.

Out of Scope for Version One: - Fully autonomous ticket resolution or closing without human action from the support team. - Voice interface within the PLM application. - Multi-language support.

6. Core Use Cases

  1. Functional How-To Question — User asks how to perform an action (e.g., add a BOM line, submit a costing sheet for approval). Agent answers using the Confluence-sourced knowledge base with a source reference where possible.
  2. Process/Status Question — User asks where their product/style currently sits in the workflow. Agent queries the season-style status API and reports phase, owner, or pending approvals.
  3. Unresolved Issue → Ticket Creation — Agent recognizes it lacks a grounded answer, informs the user it will raise a ticket rather than guessing, classifies the intent to the correct domain, creates the ServiceNow ticket with a clean technical summary, assigns it to the correct group, and returns the ticket number.
  4. Ticket Status Follow-Up — User provides a ticket number or asks about open tickets; agent queries ServiceNow and reports status (new, in progress, pending approval, resolved, etc.) in plain language.
  5. Ticket Update/Cancel — User provides new information on an existing ticket, or requests cancellation; agent updates ServiceNow accordingly.
  6. Ticket List/Search — User asks "what tickets have I opened this month" or looks up a specific ticket number.
  7. Ambiguous/Multi-Intent Question — Agent asks a clarifying question before proceeding, rather than guessing the wrong assignment group.
  8. Escalation Context Handoff — Ticket includes a clean technical summary so the assigned support team doesn't need the user to repeat themselves.
  9. Human Escalation — If the user is stuck or dissatisfied, the agent offers a clean handoff path to a live support person.

7. Functional Requirements

Knowledge and Answering: - RAG grounded strictly in the ingested Confluence knowledge base (module-wise, domain-specific documentation). - Periodic or webhook-based sync to keep the index current with Confluence edits. - Confidence thresholding — agent must not fabricate answers; low-confidence cases trigger a clarifying question or ticket fallback. - Source citations included in answers where feasible.

Intent and Domain Classification: - Classify each user query into a PLM domain (costing, BOM, line planning, library/master data, general navigation, platform/technical). - Map each domain to a ServiceNow assignment group via a configurable lookup, not hardcoded logic, so new domains/teams can be added without code changes.

Process and Status Lookup: - Integration with the existing season-style status API; respects the requesting user's permissions. - Returns current phase, status, and pending approvals for a specific product/style.

ServiceNow Integration: - Create, read, update, cancel, and list/search tickets via ServiceNow MCP server (preferred) or REST Table API (fallback) — no user login to ServiceNow required. - Auto-populate short description, clean technical summary, category, and assignment group. - Return the generated ticket number to the user immediately. - Support listing a user's tickets by time range, and lookup by specific ticket number. - Attach only a clean, technical, non-sensitive summary — never raw conversation transcripts — per SOX compliance.

Fallback and Escalation Logic: - Proactively offer ticket creation when confidence is low after reasonable attempts/clarification — never present an ungrounded answer as fact. - Clear handoff path to human support when needed.

Conversation and Session Handling: - Maintain context within a session (no repeated information from the user). - Support returning users referencing a previous ticket number in a new session.

8. Non-Functional Requirements (Production-Grade)

Security and Access Control: - SSO integration via Okta; all data queries and ticket actions scoped to the requesting user's actual permissions. - Least-privilege scoped service account credentials for the ServiceNow integration.

Compliance: - SOX-aware handling: tickets carry cleaned technical summaries only, never raw sensitive conversational content (e.g., budget, personnel, or other business-sensitive remarks).

Reliability and Resilience: - Graceful degradation if the PLM status API or ServiceNow is unavailable — clear user messaging instead of silent failure or hallucination. - Retry/backoff logic for downstream API calls.

Observability and Audit: - Full logging of every ticket creation/update/cancellation, traceable back to the originating conversation. - Admin/support dashboard: ticket volume, deflection rate, routing accuracy, common unresolved topics.

Performance: - Conversational responses within a few seconds for knowledge questions; status/ticket operations bounded by downstream API latency.

Abuse Protection: - Rate limiting per user/session to prevent runaway ticket creation or API abuse.

Extensibility: - Assignment-group mappings and knowledge base content maintainable by support/content teams without engineering involvement.

9. High-Level Solution Approach

Consistent with existing internal agent architecture patterns (Google ADK-based), an intent classification layer routes between RAG-based knowledge answering and structured API calls (status lookups), backed by a dedicated ServiceNow integration layer (MCP-first) handling the full ticket lifecycle. Confluence content is ingested into a vector store rather than queried live. The technical design document will define the specific orchestration framework, confidence-scoring mechanism, MCP vs. REST decision criteria, and the observability/dashboard stack.

10. Production Readiness Gaps and Recommendations

The following areas are not yet covered above but are typically required to run this kind of agent as a real production service rather than a proof of concept.

Evaluation and Quality Framework - Gap: No defined method to measure answer accuracy, groundedness, or routing correctness before or after launch. - Recommendation: Stand up an evaluation harness (RAGAS-style, or equivalent) with a curated test set of representative questions per domain (costing, BOM, line planning, library). Track groundedness, answer relevancy, and routing accuracy as regression gates before any knowledge base or prompt change ships. Re-run the eval suite on a schedule (e.g., weekly) against production traffic samples to catch drift.

Deployment and Environment Strategy - Gap: No defined dev/staging/production promotion path, CI/CD pipeline, or rollback plan for agent logic or knowledge base updates. - Recommendation: Use a trunk-based development flow with image promotion across dev → staging → prod (consistent with patterns already used on other GCP projects). Version the knowledge base index alongside code so a bad ingestion or prompt change can be rolled back independently of application code. Require staging validation against the eval suite before promoting to production.

Data Retention Policy - Gap: No defined retention or purge policy for conversation logs, audit trails, or ticket-linked context. - Recommendation: Define a retention window (e.g., 90 days for raw conversation logs, longer for audit-only metadata like ticket IDs and timestamps) in partnership with Nike's data governance and compliance teams, given the SOX considerations already identified. Ensure logs are purged or archived automatically rather than accumulating indefinitely.

Prompt Injection and Adversarial Input Protection - Gap: No explicit guardrails against users attempting to manipulate the agent into fabricating answers, bypassing the confidence threshold, or misusing its ServiceNow tool access (e.g., trying to get it to create, cancel, or modify tickets it shouldn't). - Recommendation: Add input sanitization and instruction-hierarchy enforcement so user messages can't override system-level rules. Constrain tool-calling permissions tightly (e.g., a user can only update/cancel their own tickets, never arbitrary ticket numbers). Log and alert on suspicious patterns, such as repeated attempts to extract system prompts or force ungrounded answers.

Service Level Agreement (SLA) - Gap: "Operate reliably" is stated as a goal without a concrete target. - Recommendation: Define explicit targets, for example 99.5% uptime, sub-3-second response time for knowledge questions, and a defined maximum for status/ticket operations bounded by ServiceNow/API latency. Track these in the observability dashboard alongside deflection rate and routing accuracy.

Knowledge Base Ownership and Governance - Gap: No owner assigned for keeping Confluence content accurate, current, and well-structured for retrieval. - Recommendation: Assign a content owner or rotating responsibility within the PLM support/product team to review and update source Confluence pages on a regular cadence (e.g., monthly), and to review the eval suite results for recurring "unanswerable" topics that signal a documentation gap.

Cost and Model Usage Monitoring - Gap: No mention of token usage, API cost tracking, or budget guardrails at production scale. - Recommendation: Instrument token/API usage per conversation and per ServiceNow/status API call, with dashboards and alerting on cost anomalies. Consider model-tiering (a smaller/cheaper model for intent classification, a stronger model only for final answer generation) to control cost at scale.

11. Remaining Open Items for Technical Design Phase

  • Exact confidence threshold definition for the fallback-to-ticket trigger.
  • Whether any human-in-the-loop review is needed before ticket auto-assignment.
  • Confluence sync frequency and mechanism (webhook vs. scheduled).
  • ServiceNow instance version check to confirm MCP server availability, or REST API fallback plan.
  • Dashboard tooling choice for observability/admin reporting.
