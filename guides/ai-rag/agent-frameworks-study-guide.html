Study Guide · LLM Orchestration

LangChain, LangGraph & CrewAI

Three frameworks that solve overlapping problems at different levels of structure: chaining LLM calls, orchestrating stateful multi-step graphs, and coordinating teams of role-based agents. This guide covers core concepts, a runnable example, and when to reach for each.

The shape of each diagram is the mental model: a chain runs once through, a graph can branch and loop back, a crew delegates by role.

LangChain

composable chains

A library of building blocks — prompts, models, retrievers, parsers — wired together with LCEL (LangChain Expression Language) using the | pipe operator. Best for linear-to-moderately-branching pipelines: RAG, summarization, extraction, tool-calling chains.

Runnable

The core interface. Every component — prompt, model, retriever, parser — implements invoke / batch / stream, so they compose uniformly.

LCEL pipe (|)

Chains Runnables left to right: output of one becomes input of the next. prompt | model | parser is a complete pipeline.

RunnableParallel

Runs multiple Runnables concurrently on the same input and merges results into a dict — the fan-out primitive.

Retriever / VectorStore

Standard interface for embedding-backed document retrieval, the backbone of RAG chains.

$ pip install langchain langchain-openai
Example — a RAG-style chain with LCEL
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough
from langchain_community.vectorstores import FAISS

# 1. Build a retriever over your docs
embeddings = OpenAIEmbeddings()
vectorstore = FAISS.from_texts(
    ["PLM tickets are triaged by the CP&I platform team.",
     "Escalations over 48h auto-route to the on-call architect."],
    embedding=embeddings,
)
retriever = vectorstore.as_retriever(search_kwargs={"k": 2})

# 2. Prompt + model + parser
prompt = ChatPromptTemplate.from_template(
    """Answer using only the context below.

Context: {context}
Question: {question}"""
)
model = ChatOpenAI(model="gpt-4o-mini", temperature=0)
parser = StrOutputParser()

# 3. Compose with LCEL — this IS the whole chain
chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | model
    | parser
)

result = chain.invoke("How are escalations routed?")
print(result)
Reach for LangChain when you need a well-trodden, mostly linear pipeline — RAG lookup, document QA, extraction — and want the huge library of prebuilt integrations (vector stores, loaders, tool wrappers) more than fine-grained control flow.
Example — tool-calling agent (ReAct-style)
from langchain_core.tools import tool
from langgraph.prebuilt import create_react_agent
from langchain_openai import ChatOpenAI

@tool
def lookup_ticket_status(ticket_id: str) -> str:
    """Look up the status of a PLM support ticket by ID."""
    # call an internal API / DB here
    return f"Ticket {ticket_id} is In Progress, assigned to platform-team."

model = ChatOpenAI(model="gpt-4o-mini")
agent = create_react_agent(model, tools=[lookup_ticket_status])

# The model decides, at each step, whether to call a tool or answer directly —
# this decide -> act -> observe loop is the "ReAct" pattern LangChain popularized.
result = agent.invoke({"messages": [("user", "What's the status of ticket PLM-4021?")]})
print(result["messages"][-1].content)

Note: as of recent LangChain versions, agent execution itself has effectively moved onto LangGraph under the hood (create_react_agent ships from langgraph.prebuilt) — LangChain still owns the tool/prompt/model abstractions, LangGraph owns the loop that drives them. This is a favorite interview distinction — see the Q&A section below.

LangGraph

stateful graphs

Built by the LangChain team for cases a linear chain can't express: branching, loops, retries, human-in-the-loop pauses, and explicit shared state. You define a graph of nodes (functions) and edges (including conditional ones) over a typed state object.

StateGraph

The graph builder. Defined over a schema (usually a TypedDict) that every node reads from and writes back to.

Nodes

Plain Python functions: state -> partial state update. Can call an LLM, a tool, or just transform data.

Conditional edges

A router function inspects state and returns the name of the next node — this is how branching and loops are expressed.

Checkpointer

Persists state between steps, enabling pause/resume, human approval gates, and time-travel debugging.

$ pip install langgraph langchain-openai
Example — a loop with a conditional retry edge
from typing import TypedDict
from langgraph.graph import StateGraph, END
from langchain_openai import ChatOpenAI

class AgentState(TypedDict):
    query: str
    draft: str
    attempts: int
    approved: bool

model = ChatOpenAI(model="gpt-4o-mini")

def draft_answer(state: AgentState) -> dict:
    resp = model.invoke(f"Answer concisely: {state['query']}")
    return {"draft": resp.content, "attempts": state["attempts"] + 1}

def critique(state: AgentState) -> dict:
    ok = len(state["draft"]) > 40  # stand-in quality check
    return {"approved": ok}

def route_after_critique(state: AgentState) -> str:
    if state["approved"] or state["attempts"] >= 3:
        return "end"
    return "retry"

graph = StateGraph(AgentState)
graph.add_node("draft", draft_answer)
graph.add_node("critique", critique)
graph.set_entry_point("draft")
graph.add_edge("draft", "critique")
graph.add_conditional_edges(
    "critique", route_after_critique, {"retry": "draft", "end": END}
)

app = graph.compile()
final_state = app.invoke({"query": "Summarize CDC vs snapshot ETL", "attempts": 0, "draft": "", "approved": False})
print(final_state["draft"])
Reach for LangGraph when the workflow genuinely branches or loops — retries until a quality bar is met, human-approval checkpoints, multi-turn agent reasoning with tool calls — and you need explicit, inspectable control over state and control flow.
Example — checkpointing for persistence & human-in-the-loop
from langgraph.checkpoint.memory import MemorySaver

checkpointer = MemorySaver()
app = graph.compile(checkpointer=checkpointer, interrupt_before=["critique"])

config = {"configurable": {"thread_id": "session-42"}}

# Run stops right before "critique" — e.g. to let a human review the draft
app.invoke({"query": "...", "attempts": 0, "draft": "", "approved": False}, config)

# Later — possibly a different process entirely — resume the same thread:
app.invoke(None, config)  # continues from the checkpointed state

The thread_id is what lets a graph pause for days (waiting on a human, an external event, a Slack approval) and resume exactly where it left off — this is the mechanism behind LangGraph's human-in-the-loop story, and a common whiteboard question.

CrewAI

role-based agent teams

A higher-level, opinionated framework built around a team metaphor: each agent has a role, a goal, and a backstory; tasks are assigned to agents; a crew coordinates execution sequentially or hierarchically (with a manager agent delegating).

Agent

Defined by role, goal, backstory, and optional tools — the persona and capability of a worker.

Task

A unit of work with a description and expected_output, assigned to one agent; can depend on prior tasks' outputs via context.

Crew

The container that runs agents against tasks, in Process.sequential or Process.hierarchical mode.

Process.hierarchical

Adds an implicit manager agent that plans, delegates tasks to workers, and reviews their output.

$ pip install crewai crewai-tools
Example — a two-agent research & writing crew
from crewai import Agent, Task, Crew, Process

researcher = Agent(
    role="Senior Researcher",
    goal="Find accurate, current facts on the given topic",
    backstory="A meticulous analyst who never states a claim without a source.",
    verbose=True,
)

writer = Agent(
    role="Technical Writer",
    goal="Turn research notes into a clear, concise brief",
    backstory="A writer who values plain language over jargon.",
    verbose=True,
)

research_task = Task(
    description="Research the tradeoffs of CDC vs snapshot-based ETL.",
    expected_output="5 bullet points with key tradeoffs.",
    agent=researcher,
)

write_task = Task(
    description="Write a 150-word brief for a platform team using the research.",
    expected_output="A short, plain-language brief.",
    agent=writer,
    context=[research_task],  # chains this task's input to research_task's output
)

crew = Crew(
    agents=[researcher, writer],
    tasks=[research_task, write_task],
    process=Process.sequential,
)

result = crew.kickoff()
print(result)
Reach for CrewAI when the problem naturally decomposes into specialist roles collaborating — researcher + writer, planner + coder + reviewer — and you want role/goal/backstory framing plus delegation out of the box, without hand-building the orchestration graph yourself.
Example — hierarchical process with a manager agent
crew = Crew(
    agents=[researcher, writer],
    tasks=[research_task, write_task],
    process=Process.hierarchical,      # adds an implicit manager
    manager_llm="gpt-4o",             # the manager agent's own model
    memory=True,                       # shared short-term memory across the crew
)

result = crew.kickoff()

In hierarchical mode you don't assign tasks to agents directly — the manager agent decides delegation at runtime based on each worker's role/goal. That's the key structural difference from Process.sequential, and it's the CrewAI analog of LangGraph's supervisor pattern.

Comparison table

LangChain LangGraph CrewAI
Mental model Pipe (|) of Runnables Graph of nodes + edges over shared state Team of role-based agents + tasks
Control flow Mostly linear, some branching Arbitrary — branches, loops, cycles Sequential or hierarchical (delegated)
State Implicit, passed through the pipe Explicit typed state object Implicit, passed via task context
Best fit RAG, extraction, tool-calling chains Multi-step agents, retries, human-in-loop Multi-persona collaborative workflows
Learning curve Low–medium Medium–high Low

Which one to reach for

Start with LangChain

if the task is "retrieve → prompt → parse" and you want the ecosystem of integrations.

Move to LangGraph

the moment you need a loop, a conditional branch, a retry, or a pause for human approval.

Choose CrewAI

when the problem is naturally a team of specialists and you want that framing without building the graph by hand.

In practice these compose: a CrewAI agent can use LangChain tools internally, and a LangGraph node can call a LangChain chain — they are not mutually exclusive choices.

Common interview Q&A

Grouped by framework. Click to expand — answers are written the way you'd say them out loud, not textbook definitions.

LangChain

What's the difference between the old LangChain Chain classes and LCEL?
Legacy classes like LLMChain and SequentialChain hard-coded their composition logic in Python subclasses. LCEL replaces that with the Runnable interface and the | operator, so any two components compose the same way. LCEL chains also get streaming, async, and batch support for free, plus automatic parallelization via RunnableParallel — none of which the legacy classes gave you uniformly.
How does LangChain handle conversation memory?
The old ConversationBufferMemory-style classes are considered legacy now. The current pattern is to manage message history explicitly — store a list of messages per session (often in Redis or a DB) and pass it in as part of the input, or use RunnableWithMessageHistory to wrap a chain and inject history automatically keyed by a session id. Worth saying in an interview: memory is "just state you pass in," not framework magic.
How do you handle a tool call that fails or returns malformed output?
  • Wrap tool execution and catch exceptions, returning a structured error string back to the model so it can retry or choose another tool rather than crashing the run.
  • Use with_structured_output or a Pydantic-backed output parser so malformed JSON raises early and can trigger a retry via RunnableRetry / .with_retry().
  • Set a max retry / max iteration cap — an agent that keeps calling a broken tool in a loop is the single most common production incident with agentic chains.
How would you reduce latency in a LangChain RAG pipeline?
  • Stream tokens (.stream()) so perceived latency drops even if total time doesn't.
  • Run independent steps concurrently with RunnableParallel (e.g. retrieval + query rewriting).
  • Cache embeddings and, where safe, cache full responses for repeated queries.
  • Trim context — retrieve fewer, higher-precision chunks rather than a large k and let the model sort it out.

LangGraph

Why would you choose LangGraph over just writing a Python state machine by hand?
You'd get most of the control flow for free either way — the value LangGraph adds is the surrounding infrastructure: built-in checkpointing/persistence, first-class streaming of intermediate node outputs, human-in-the-loop interrupts, time-travel debugging (replay from any checkpoint), and a visualizable graph structure. For a one-off script, hand-rolled is fine. For anything that needs to pause, resume, or be inspected in production, LangGraph earns its keep.
Explain the "supervisor" multi-agent pattern in LangGraph.
A supervisor node is an LLM call whose only job is to look at the current state and decide which specialist node/agent should run next, returning that as a routing decision consumed by a conditional edge. Each specialist runs, control returns to the supervisor, and the loop continues until the supervisor decides to end. It's functionally the graph-native equivalent of CrewAI's hierarchical process — same idea, more explicit wiring.
How does LangGraph prevent infinite loops?
There's a recursion_limit (default 25 super-steps) passed via config that raises a GraphRecursionError once exceeded. Beyond that hard stop, well-designed graphs carry their own loop counter in state (as in the retry example above) and route to END once a max-attempts threshold is hit — relying only on the framework's default limit is a common design smell to call out.
What's the difference between a checkpointer and long-term memory in LangGraph?
A checkpointer persists the full graph state for one thread_id — it's how a single conversation/run survives pauses and restarts. Long-term memory (the Store interface) is cross-thread: facts that should be retrievable in a different conversation entirely, like user preferences. Interviewers like this distinction because it maps directly to "session state" vs "user profile" in traditional app architecture.

CrewAI

How does CrewAI decide which agent handles which task?
In Process.sequential, the assignment is explicit — you set agent= on each Task. In Process.hierarchical, there's no explicit assignment: an auto-created manager agent reads each agent's role/goal and the task list, then delegates at runtime, similar to how a human project manager would assign work based on who's best suited.
How do agents share information between tasks in CrewAI?
Via the context parameter on a Task — passing a list of upstream Task objects makes their outputs available as input to the current task. There's also crew-level memory=True for shared short-term memory across the run, and CrewAI supports long-term memory backed by a vector store for recall across separate kickoff() calls.
When would CrewAI be the wrong choice?
When you need fine-grained control over exactly when and how control passes between steps — CrewAI's delegation logic in hierarchical mode is somewhat opaque compared to an explicit LangGraph edge. If a bug requires you to reason precisely about "why did step 3 run before step 2," a graph you wired yourself is easier to debug than an emergent delegation decision.

Cross-framework

Can these three be combined in one system?
Yes, and it's a good answer to "how would you architect this" questions. A common pattern: LangChain provides the model/tool/retriever abstractions, LangGraph wraps them into a controlled, stateful orchestration loop, and a CrewAI crew (or a single specialist agent) can be invoked as a tool/node from within that graph for a sub-task that benefits from role-based framing. They solve different layers of the same problem, not competing ones.
How do you evaluate and monitor an agent in production?
  • Tracing — LangSmith (native to LangChain/LangGraph) or an OpenTelemetry-based tracer captures every LLM call, tool call, and state transition for a run.
  • Evals — a fixed set of test inputs with expected behaviors, run on every change; for agentic loops this includes checking the tool-call sequence, not just the final answer.
  • Guardrails — max iteration/recursion caps, timeouts, and cost ceilings per run so a stuck loop can't run away.
  • Human review sampling — spot-check a percentage of production traces, especially ones that hit a retry or fallback path.
How do you control cost in an agentic pipeline?
Route by task difficulty — cheap/fast model for routing and simple extraction, stronger model only for the step that needs it. Cap max tool calls and max loop iterations. Cache aggressively (embeddings, retrieval results, repeated prompts). Truncate conversation history/context rather than letting it grow unbounded across turns.

Gotchas & tradeoffs

The kind of nuance that separates "used a tutorial" from "shipped it" — good material for follow-up questions.

!
Agents can loop forever on a flaky tool.

Without an explicit attempt counter in state (LangGraph) or a max-iteration setting, a model that keeps getting an error from a tool will often just keep calling it. Always cap iterations and treat "give up gracefully" as a designed path, not an afterthought.

!
LCEL's implicit state passing gets messy past 4–5 steps.

Because data flows through the pipe rather than a named state object, a long LCEL chain becomes hard to debug — you can't easily inspect "what was the value of X after step 3." This is precisely the pressure that pushes teams from LangChain chains to LangGraph as complexity grows.

!
CrewAI's hierarchical delegation is non-deterministic.

The manager agent's delegation decision is itself an LLM call, so the same crew can execute tasks in a different order or delegate differently across runs. Fine for many workflows, but a real constraint if you need reproducible execution order for audit or debugging.

!
Vector store retrieval quality, not the chain logic, is usually the actual bottleneck.

Teams often spend time tuning prompts and chain structure when the real problem is chunking strategy, embedding model choice, or missing metadata filters. Worth mentioning if asked to debug a "the RAG answers are wrong" scenario.

!
Checkpointer choice matters at scale.

MemorySaver is in-process only — fine for a demo, gone on restart. Production LangGraph deployments need a durable checkpointer (Postgres, Redis) so paused threads survive a pod restart or deploy.

!
Framework version churn.

All three frameworks moved fast through 2024–2025 — agent execution moved from LangChain into LangGraph, memory APIs were reworked, CrewAI's flows feature was added alongside crews. Naming a specific version or saying "verify against current docs" reads as more credible than assuming an API surface is stable.

Production readiness checklist

Useful framing for "how would you take this to production" questions — organize your answer around these four buckets.

Reliability

  • Timeouts on every LLM and tool call
  • Retry with backoff on transient failures only
  • Max iteration / recursion caps
  • Fallback model or canned response path

Observability

  • Full tracing (LangSmith / OpenTelemetry)
  • Per-run cost & token tracking
  • Structured logs keyed by thread_id/session
  • Alerting on loop/iteration-cap hits

Quality

  • Regression eval suite run pre-deploy
  • Tool-call sequence checks, not just final output
  • Human-in-the-loop gate for high-stakes actions
  • Sampled human review of production traces

Cost & latency

  • Model routing by task difficulty
  • Caching (embeddings, retrieval, repeat prompts)
  • Streaming for perceived latency
  • Context/history trimming per turn

Practice system design prompt

"Design an internal agent that answers employee questions against a knowledge base, can escalate to a human, and can trigger a ticket creation tool."

A strong answer walks through, in order:

  • Retrieval layer — LangChain vector store + retriever over the knowledge base, with metadata filters (team, doc freshness).
  • Orchestration layer — a LangGraph graph: a router node classifies intent (answerable / needs escalation / needs a ticket), branches accordingly, and loops back to retrieval if the first answer is low-confidence.
  • Tools — ticket-creation and escalation-to-human as LangChain tools the graph's nodes can call, with a interrupt_before human-approval gate before any ticket is actually filed.
  • Persistence — a durable checkpointer so a mid-conversation escalation can wait on a human without holding a process open.
  • Where CrewAI could fit — if "answer the question" itself decomposes into research + drafting sub-steps, that inner piece could be a small crew invoked as one LangGraph node, rather than modeling that whole sub-flow as more graph edges.
  • Guardrails — iteration caps, cost tracking per session, and eval coverage on the router's classification accuracy specifically, since misrouting is the highest-impact failure mode.
