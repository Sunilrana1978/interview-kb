Implementing Context Management Strategies — GCP & AWS

Step-by-step implementation with code for each of the six strategies, on both Google ADK / Vertex AI and AWS Bedrock stacks.

1. Sub-Agent Isolation (Context Scoping)

Goal: Each sub-agent gets a narrow, task-scoped context — not the full conversation.

On GCP — Google ADK

Steps: 1. Define a root/orchestrator agent with sub_agents=[...]. 2. Give each sub-agent its own instruction and tools — do not pass shared conversation state by default. 3. Use output_key so a sub-agent’s result is written to session state as a single clean value, not the full transcript.

from google.adk.agents import Agent

# Sub-agent: only sees its own scoped task, not the full conversation
ticketing_agent = Agent(
    name="ticketing_agent",
    model="gemini-2.5-flash",
    instruction=(
        "You create ServiceNow tickets. You will receive a short task "
        "description and category. Do not ask about prior conversation — "
        "you don't have access to it. Return only the ticket number."
    ),
    tools=[create_servicenow_ticket, search_servicenow_tickets],
    output_key="ticket_result",   # written to session.state, not appended to history
)

knowledge_agent = Agent(
    name="knowledge_agent",
    model="gemini-2.5-flash",
    instruction="Answer PLM how-to questions using retrieved Confluence docs only.",
    tools=[search_confluence_kb],
    output_key="kb_answer",
)

root_agent = Agent(
    name="plm_support_orchestrator",
    model="gemini-2.5-flash",
    instruction=(
        "Route the user's question. For ticket creation, call ticketing_agent "
        "with ONLY the ticket summary and category — not the full chat history. "
        "For how-to questions, call knowledge_agent with only the question."
    ),
    sub_agents=[ticketing_agent, knowledge_agent],
)
  1. Deploy each agent as its own Cloud Run service if you want hard process isolation (not just prompt isolation) — call sub-agents over HTTP with a minimal JSON payload instead of in-process.

On AWS — Bedrock Agents / AgentCore

Steps: 1. Create separate Bedrock Agents per responsibility (one for retrieval, one for ticketing/action). 2. Use an orchestrator Lambda (or a supervisor agent in Bedrock AgentCore) that constructs a minimal prompt per sub-agent call — never forwards the full DynamoDB session history. 3. Pass only structured fields via the sessionState.sessionAttributes field, not free text history.

import boto3

bedrock_agent_runtime = boto3.client("bedrock-agent-runtime")

def invoke_scoped_subagent(agent_id, alias_id, task_summary, category):
    """Call a sub-agent with ONLY the scoped task — not full session history."""
    response = bedrock_agent_runtime.invoke_agent(
        agentId=agent_id,
        agentAliasId=alias_id,
        sessionId=f"scoped-{category}-{task_summary[:8]}",  # fresh scoped session
        inputText=f"Category: {category}\nTask: {task_summary}",
        sessionState={
            "sessionAttributes": {"category": category}  # structured, not narrative
        },
    )
    return "".join(
        chunk["chunk"]["bytes"].decode("utf-8")
        for chunk in response["completion"]
        if "chunk" in chunk
    )

# Orchestrator Lambda handler
def orchestrator_handler(event, context):
    intent = classify_intent(event["userMessage"])  # cheap, small-context call
    if intent == "create_ticket":
        return invoke_scoped_subagent(
            TICKETING_AGENT_ID, TICKETING_ALIAS_ID,
            task_summary=extract_ticket_summary(event["userMessage"]),
            category=intent,
        )
    return invoke_scoped_subagent(KB_AGENT_ID, KB_ALIAS_ID, event["userMessage"], intent)

2. Compaction / Rolling Summarization

Goal: Compress old turns into a summary; keep structured facts separate and untouched.

On GCP — Vertex AI + Firestore/Cloud SQL for state

Steps: 1. Track token count per session (Vertex AI returns usage_metadata.total_token_count). 2. When it crosses a threshold (e.g., 60% of your working budget), trigger a summarization call. 3. Store the summary and a separate facts object in Firestore; only load facts verbatim, always.

from google import genai
from google.cloud import firestore

client = genai.Client()
db = firestore.Client()

COMPACTION_THRESHOLD = 60_000  # tokens

def maybe_compact(session_id: str, messages: list, facts: dict):
    total_tokens = client.models.count_tokens(
        model="gemini-2.5-flash", contents=messages
    ).total_tokens

    if total_tokens < COMPACTION_THRESHOLD:
        return messages, facts

    # Summarize narrative only — facts are never passed through summarization
    summary_resp = client.models.generate_content(
        model="gemini-2.5-flash",
        contents=[
            "Summarize this support conversation in under 200 words. "
            "Do not include IDs, ticket numbers, or exact figures — "
            "those are tracked separately.\n\n" + format_messages(messages)
        ],
    )
    summary = summary_resp.text

    db.collection("sessions").document(session_id).set(
        {"summary": summary, "facts": facts, "updated_at": firestore.SERVER_TIMESTAMP},
        merge=True,
    )

    # New context = summary + last 2 turns + facts (facts injected separately, structured)
    compacted = [{"role": "system", "text": f"Prior context summary: {summary}"}] + messages[-2:]
    return compacted, facts
  1. On every tool call that produces a durable fact (ticket ID, status), update facts directly — never let it pass through the summarizer.

On AWS — Bedrock + DynamoDB

Steps: 1. Use a DynamoDB table with two attributes per session: summary (string) and facts (map) — updated independently. 2. Trigger compaction in a Lambda when message count or estimated token size crosses a threshold.

import boto3
from decimal import Decimal

bedrock_runtime = boto3.client("bedrock-runtime")
dynamodb = boto3.resource("dynamodb").Table("agent_sessions")

def compact_session(session_id: str, messages: list, facts: dict):
    prompt = (
        "Summarize this conversation in under 200 words. "
        "Exclude any IDs or exact figures.\n\n" + format_messages(messages)
    )
    resp = bedrock_runtime.converse(
        modelId="anthropic.claude-sonnet-4-6",
        messages=[{"role": "user", "content": [{"text": prompt}]}],
        inferenceConfig={"maxTokens": 400},
    )
    summary = resp["output"]["message"]["content"][0]["text"]

    dynamodb.update_item(
        Key={"session_id": session_id},
        UpdateExpression="SET summary = :s, facts = :f",
        ExpressionAttributeValues={":s": summary, ":f": facts},
    )
    return summary, facts
  1. On load, always merge facts back in verbatim: context = [summary] + facts_as_structured_block + recent_messages.

3. Just-in-Time Retrieval (RAG, Not Context Stuffing)

Goal: Retrieve only the chunks needed for the current step, scoped by domain/intent.

On GCP — Vertex AI Vector Search / Gemini File Search

Steps: 1. Ingest Confluence docs per-domain (costing, BOM, line planning) into separate File Search stores or separate namespaces in one Vector Search index. 2. Run intent classification first (cheap call) to pick the domain. 3. Query only that domain’s index — not the full corpus.

from google import genai

client = genai.Client()

DOMAIN_STORES = {
    "costing": "projects/nike-plm/locations/us-central1/ragCorpora/costing-kb",
    "bom": "projects/nike-plm/locations/us-central1/ragCorpora/bom-kb",
    "line_planning": "projects/nike-plm/locations/us-central1/ragCorpora/lineplanning-kb",
}

def classify_domain(question: str) -> str:
    resp = client.models.generate_content(
        model="gemini-2.5-flash-lite",   # cheap, small model for routing
        contents=f"Classify into one word: costing, bom, or line_planning.\nQ: {question}",
    )
    return resp.text.strip().lower()

def answer_scoped(question: str):
    domain = classify_domain(question)
    store = DOMAIN_STORES.get(domain)

    resp = client.models.generate_content(
        model="gemini-2.5-flash",
        contents=question,
        config={
            "tools": [{
                "retrieval": {
                    "vertex_rag_store": {"rag_corpora": [store]}
                }
            }]
        },
    )
    return resp.text

On AWS — Bedrock Knowledge Bases + OpenSearch Serverless

Steps: 1. Create separate Bedrock Knowledge Bases per domain (or use metadata filtering on one OpenSearch collection with a domain field). 2. Filter retrieval by domain metadata at query time.

import boto3

bedrock_agent_runtime = boto3.client("bedrock-agent-runtime")

def retrieve_scoped(question: str, domain: str, kb_id: str):
    response = bedrock_agent_runtime.retrieve(
        knowledgeBaseId=kb_id,
        retrievalQuery={"text": question},
        retrievalConfiguration={
            "vectorSearchConfiguration": {
                "numberOfResults": 5,
                "filter": {
                    "equals": {"key": "domain", "value": domain}  # scoped, not full corpus
                },
            }
        },
    )
    return [r["content"]["text"] for r in response["retrievalResults"]]
  1. For the “cheap relevance pass before retrieval” refinement: run a lightweight Bedrock Titan or Claude Haiku-class call to check if retrieval is even needed before firing the full retrieve-and-generate call.

4. Structured External Memory (“Scratchpads”)

Goal: Durable facts live outside the LLM context, in a schema, with provenance.

On GCP — Firestore as structured memory

Steps: 1. Define a schema: {fact_key, value, source_agent, source_doc, updated_at}. 2. Agents read/write to this store via a tool, not via conversation text.

from google.cloud import firestore

db = firestore.Client()

def write_fact(session_id: str, key: str, value, source_agent: str, source_ref: str):
    db.collection("sessions").document(session_id).collection("facts").document(key).set({
        "value": value,
        "source_agent": source_agent,
        "source_ref": source_ref,   # e.g., Confluence page ID, ServiceNow ticket ID
        "updated_at": firestore.SERVER_TIMESTAMP,
    })

def read_facts(session_id: str) -> dict:
    docs = db.collection("sessions").document(session_id).collection("facts").stream()
    return {d.id: d.to_dict() for d in docs}

# Expose as an ADK tool so agents call it explicitly rather than relying on context
def get_known_facts_tool(session_id: str) -> str:
    facts = read_facts(session_id)
    return "\n".join(f"{k}: {v['value']} (source: {v['source_ref']})" for k, v in facts.items())

On AWS — DynamoDB as structured memory with provenance

Steps: 1. Single-table design: PK = session_id, SK = fact#<key>, attributes for value/source/timestamp.

import boto3
from datetime import datetime, timezone

table = boto3.resource("dynamodb").Table("agent_memory")

def write_fact(session_id, key, value, source_agent, source_ref):
    table.put_item(Item={
        "PK": session_id,
        "SK": f"fact#{key}",
        "value": value,
        "source_agent": source_agent,
        "source_ref": source_ref,
        "updated_at": datetime.now(timezone.utc).isoformat(),
    })

def read_facts(session_id):
    resp = table.query(
        KeyConditionExpression="PK = :pk AND begins_with(SK, :prefix)",
        ExpressionAttributeValues={":pk": session_id, ":prefix": "fact#"},
    )
    return {item["SK"].split("#", 1)[1]: item for item in resp["Items"]}
  1. Wire write_fact as a Bedrock Agent action-group function so tool results write here directly instead of only living in the conversation transcript.

5. Orchestrator–Worker Context Routing

Goal: A router does cheap intent classification, then builds a minimal, task-specific payload — nothing is broadcast by default.

On GCP — ADK root agent + versioned routing config

Steps: 1. Keep routing rules in a small YAML/JSON spec, not buried in a growing system prompt. 2. Root agent classifies intent, looks up the target sub-agent from config, sends only relevant fields.

# routing_config.yaml — versioned, testable, reviewed like code
routes:
  - intent: create_ticket
    agent: ticketing_agent
    required_fields: [summary, category]
  - intent: how_to_question
    agent: knowledge_agent
    required_fields: [question, domain]
  - intent: check_status
    agent: status_agent
    required_fields: [program_id]
import yaml

with open("routing_config.yaml") as f:
    ROUTES = {r["intent"]: r for r in yaml.safe_load(f)["routes"]}

def route(intent: str, extracted_fields: dict):
    route_def = ROUTES[intent]
    payload = {k: extracted_fields[k] for k in route_def["required_fields"]}
    return call_agent(route_def["agent"], payload)  # minimal payload only

On AWS — Step Functions as the router

Steps: 1. Use a Step Functions state machine with a Choice state for routing — routing logic is versioned infrastructure-as-code, not prompt text. 2. Each branch invokes a Lambda that builds a minimal, scoped payload for its target Bedrock Agent.

{
  "Comment": "Context-scoped routing for PLM support",
  "StartAt": "ClassifyIntent",
  "States": {
    "ClassifyIntent": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:xxx:function:classify-intent",
      "Next": "RouteByIntent"
    },
    "RouteByIntent": {
      "Type": "Choice",
      "Choices": [
        {"Variable": "$.intent", "StringEquals": "create_ticket", "Next": "InvokeTicketing"},
        {"Variable": "$.intent", "StringEquals": "how_to_question", "Next": "InvokeKnowledge"}
      ],
      "Default": "InvokeKnowledge"
    },
    "InvokeTicketing": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:xxx:function:invoke-ticketing-agent",
      "End": true
    },
    "InvokeKnowledge": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:xxx:function:invoke-knowledge-agent",
      "End": true
    }
  }
}

6. Tool-Result Pruning

Goal: Extract durable facts from tool output, then discard the raw payload.

On GCP — ADK tool wrapper pattern

Steps: 1. Wrap every tool call with a post-processing step that extracts only what’s needed before it re-enters context.

def search_servicenow_tickets_pruned(query: str) -> str:
    raw_results = search_servicenow_tickets_raw(query)  # could be 40 full ticket JSONs

    # Extract only durable, compact fields — raw payload never enters context
    pruned = [
        {"id": t["number"], "status": t["state"], "category": t["category"]}
        for t in raw_results
    ]
    return f"Found {len(pruned)} tickets: " + "; ".join(
        f"{p['id']} ({p['status']})" for p in pruned
    )
  1. Register search_servicenow_tickets_pruned, not the raw function, as the ADK tool — the pruning is enforced at the tool boundary, not left to the model’s discretion.

On AWS — Lambda action group with response shaping

Steps: 1. In your Bedrock Agent action group Lambda, shape the response before returning it to the agent — this is the natural pruning point.

def lambda_handler(event, context):
    action = event["actionGroup"]
    api_path = event["apiPath"]

    if api_path == "/searchTickets":
        raw = call_servicenow_api(event["parameters"])
        pruned = [
            {"id": t["number"], "status": t["state"]}
            for t in raw["result"]
        ]
        response_body = {"application/json": {"body": json.dumps(pruned)}}
    # ... other paths

    return {
        "messageVersion": "1.0",
        "response": {
            "actionGroup": action,
            "apiPath": api_path,
            "httpMethod": event["httpMethod"],
            "httpStatusCode": 200,
            "responseBody": response_body,  # pruned, not raw ServiceNow payload
        },
    }
  1. Pair with Strategy 4: write the full extracted fact set to DynamoDB via write_fact, then return only a short confirmation string to the agent’s context.

Quick Reference — Where Each Lives in Your Stack

Strategy GCP building block AWS building block
1. Sub-agent isolation ADK sub_agents + output_key, or separate Cloud Run services Separate Bedrock Agents + orchestrator Lambda
2. Compaction Vertex AI token counting + Firestore for summary/facts split Bedrock converse + DynamoDB summary/facts split
3. Just-in-time RAG Vertex AI Vector Search / Gemini File Search, per-domain corpora Bedrock Knowledge Bases + OpenSearch metadata filtering
4. Structured memory Firestore facts subcollection with provenance fields DynamoDB single-table facts with provenance fields
5. Orchestrator routing ADK root agent + versioned YAML routing config Step Functions Choice state + Lambda
6. Tool pruning ADK tool wrapper shaping response before return Bedrock action-group Lambda shaping responseBody

Implementation order that tends to work well: start with 6 (pruning) and 3 (scoped retrieval) — they’re cheap, low-risk, and immediately cut context bloat. Add 1 (isolation) and 5 (routing) as you add more agents. Add 2 (compaction) once sessions start running long. Treat 4 (structured memory with provenance) as the foundation everything else should write into — it’s the most expensive to build right, but it’s what prevents the “agents silently disagree” failure mode.
