TECHNICAL DESIGN DOCUMENT

Multi-Agent PLM Assistant on Google ADK, Governed by a Shared LiteLLM Gateway

Architecture, deployment, and governance design for a multi-agent ADK application routed through a self-hosted LiteLLM Proxy on Google Cloud.

AuthorSunil Kumar — Cloud Architect, CP&I PLM Platform
StatusDraft for Review
Version1.0
DateAugust 15, 2026
Target platformGoogle Cloud (Cloud Run / Vertex AI Agent Engine)
Related reposlitellm-proxy, multi-agent-app

1. Overview

This document describes the design of a multi-agent assistant built on Google's Agent Development Kit (ADK), with all model calls routed through a self-hosted LiteLLM Proxy. The proxy centralizes routing, fallback, virtual keys and budgets, guardrails, cost attribution, and observability across every agent and every model provider in scope — Vertex AI/Gemini, AWS Bedrock, and Bedrock AgentCore.

The design targets Google Cloud as the primary deployment surface, with two supported paths for the agent application (Cloud Run and Vertex AI Agent Engine) and one deployment path for the shared proxy (Cloud Run, backed by Cloud SQL and Memorystore).

2. Goals and Non-Goals

2.1 Goals

  • Give every sub-agent in the multi-agent app access to any model provider (Gemini, Claude on Bedrock, future providers) through one consistent interface.
  • Enforce per-agent spend budgets and rate limits without embedding provider credentials in agent code.
  • Apply PII masking and content guardrails centrally, once, regardless of which agent or provider produced the text.
  • Produce one connected observability trace across every agent-to-agent and agent-to-model hop.
  • Support automatic fallback across providers/regions/clouds without agent-level retry logic.
  • Keep the agent application's codebase free of provider credentials and routing logic.

2.2 Non-Goals

  • This document does not cover prompt design, tool implementation details, or agent instruction tuning.
  • This document does not cover the BerriAI managed/enterprise-hosted LiteLLM offering — the design assumes self-hosted OSS.
  • Multi-region active-active failover for the proxy itself is out of scope for v1; noted as a future consideration in §12.

3. Background

The application is a 3-agent ADK system — an orchestrator that delegates to a research sub-agent and a summarizer sub-agent — supporting the PLM product development team. As a second, third, and future agent are added to the platform, calling model providers directly from each agent's code would mean duplicated credential management, no shared spend visibility, and no consistent place to enforce guardrails. LiteLLM's Proxy mode addresses this by inserting one governed gateway between every agent and every provider, matching the pattern already used for the team's separate internal-data-agent and shopping-assistant-agent projects.

4. Proposed Architecture

At the system level, the multi-agent app never calls a model provider directly. Each sub-agent is configured with a scoped virtual key and points at the shared proxy's endpoint; the proxy owns all provider credentials, routing, and governance.

5. Request Flow — Governance Pipeline

Every model call from any sub-agent passes through the same six-stage pipeline inside the proxy before it reaches a provider. This is the mechanism that lets governance be added once, centrally, rather than per agent.

Figure 2 — Request flow through the LiteLLM Proxy governance pipeline
StageWhat happensConfig surface
1. Virtual key authValidates the caller's key, checks remaining budget/RPM before proceedingPostgres (keys table)
2. GuardrailPresidio PII scan on the outbound promptguardrails.yaml, mode: pre_call
3. RouterSelects a deployment using the configured strategy (e.g. least-busy)config.yaml, router_settings
4. FallbackOn throttle/timeout, retries against the configured fallback modelconfig.yaml, fallbacks
5. Cost logCalculates and persists per-request cost, tagged by agent_name metadataPostgres (spend_logs table)
6. Trace exportPublishes the full call (prompt, tokens, latency, provider) as a Langfuse spanlitellm_settings.success_callback

6. Deployment Architecture (Google Cloud)

The proxy is deployed once as shared infrastructure. The agent application supports two deployment targets — Cloud Run or Vertex AI Agent Engine — chosen per environment; both reach the same proxy.

Figure 3 — GCP deployment and networking, including the Agent Engine private-access path

6.1 Cloud Run Path

Both the agent app and the proxy run on Cloud Run in the same VPC, connected via a Serverless VPC Access connector. The proxy is deployed with internal-only ingress; the agent app authenticates to it using its LiteLLM virtual key over HTTPS.

6.2 Vertex AI Agent Engine Path

Agent Engine runs the agent application in a Google-managed tenant project with no direct VPC membership by default. Two connectivity options apply:

  • Public HTTPS endpoint on the proxy (Cloud Run default URL or custom domain), secured by the virtual key — simplest, acceptable for most deployments.
  • Private Service Connect (PSC) interface + DNS peering — required when VPC Service Controls is enabled or public egress is disallowed; provisions a private bridge from the Agent Engine tenant project into the proxy's VPC.
Design decision

This design recommends the Cloud Run path for the agent application in production, with Agent Engine evaluated for the managed session/memory features once the team's memory requirements are finalized. Both paths use an identical LiteLlm() call signature in agent code — the target is an operational choice, not a code change.

7. SDK Mode vs. Proxy Mode — Decision

LiteLLM offers two integration modes. This design uses Proxy mode exclusively for the reasons below.

CapabilitySDK modeProxy mode
Router & load balancingYes — litellm.Router, but requires a custom ADK bridge classYes — native, shared by every consumer
Fallbacks & retriesYes, same custom bridge requiredYes — config.yaml
Virtual keys & enforced budgetsNo — no auth layer exists in-processYes — required
Guardrails / PII maskingNo — must be hand-written per callYes — declarative, centralized
Cost tracking, attributed & queryableNo persistence without custom loggingYes — spend_logs, per agent_name
Observability (Langfuse/OTel)Yes, in-process callbackYes
Credential locationEvery calling service/appProxy only (Secret Manager)

Decision: adopt Proxy mode for all agents in this application. SDK mode is not used, since the two capabilities that matter most for this design — per-agent budget enforcement and centralized guardrails — have no SDK-mode equivalent; there is no server-side state to enforce a budget against without the proxy.

8. Security and Compliance

8.1 Credential Management

  • No AWS or GCP model-provider credential is ever present in the multi-agent-app codebase or its runtime environment.
  • The proxy's Cloud Run service account authenticates to Vertex AI via IAM (roles/aiplatform.user); Bedrock credentials are read from Secret Manager at proxy startup.
  • Each sub-agent authenticates to the proxy using a scoped virtual key, not a provider credential.

8.2 PII and Guardrails

  • Presidio-based guardrail scans both the outbound prompt (pre_call) and the model's response (post_call) for PERSON, EMAIL_ADDRESS, and PHONE_NUMBER entities, masking matches before they cross either boundary.
  • Guardrail configuration lives in guardrails.yaml in the litellm-proxy repository and applies uniformly to every agent, regardless of which model served the request.

8.3 Budgets and Rate Limits

  • Each agent role (research_agent, summarizer_agent, orchestrator) is issued its own virtual key with an independent monthly budget and RPM limit.
  • A runaway or looping sub-agent is contained by its own key's budget cap and cannot exhaust another agent's allocation.

8.4 Known Operational Risk

Security note

A March 2026 supply-chain incident involved two compromised LiteLLM PyPI releases capable of exfiltrating environment and cloud credentials; the official Docker proxy image was unaffected. This design pins the proxy's Docker image to an exact, verified tag and prohibits building from :latest or main.

9. Observability and Cost Attribution

Every proxy call is tagged with agent-identifying metadata at the point of call, enabling per-agent cost and trace analysis rather than only whole-application totals.

model=LiteLlm(
    model="claude-sonnet",
    api_base=os.environ["LITELLM_PROXY_URL"],
    api_key=os.environ["RESEARCH_AGENT_VIRTUAL_KEY"],
    extra_body={"metadata": {"agent_name": "research_agent", "team": "plm-support"}},
)
  • Cost: GET /spend/logs, aggregated by metadata.agent_name, gives per-agent spend rather than one application-wide number.
  • Traces: litellm_settings.success_callback: ["langfuse"] exports every call as a span; because agent_name is already attached, one Langfuse trace shows the full path — orchestrator → research_agent (Bedrock) → summarizer_agent (Gemini) — as connected spans.

11. Alternatives Considered

AlternativeReason not selected
Call Vertex AI and Bedrock directly from each agent (no gateway)No shared budget enforcement, no centralized guardrails, credential sprawl across every agent's runtime
SDK-mode litellm.Router only, no proxy serverNo virtual keys or enforced budgets; per-agent custom bridge code required for routing/fallback
BerriAI managed/enterprise-hosted proxyRemoves ops burden but moves provider credentials and request traffic outside the team's own VPC; not aligned with existing self-hosted AWS/GCP architecture
OpenRouter or similar SaaS gatewayThird party in the request path; less control over routing logic and compliance posture than a self-hosted proxy

12. Risks and Open Questions

  • Proxy is a single shared dependency for every agent in the platform — an outage affects all consumers simultaneously. Multi-region active-active deployment is not in v1 scope; tracked as a follow-up.
  • Postgres and Redis become new operational responsibilities for the platform team — backup, failover, and upgrade cadence need an owner assigned before go-live.
  • Cross-cloud fallback (Bedrock → Vertex) has not yet been load-tested under sustained throttling; recommend a chaos test before relying on it in production.
  • Open question: whether Agent Engine's Sessions/Memory Bank (GA December 2025) should replace ADK's default session handling once memory requirements are finalized.

13. Rollout Plan

  • Phase 1: Deploy litellm-proxy to a staging Cloud Run environment with Cloud SQL/Memorystore; validate config.yaml via the CI schema check.
  • Phase 2: Provision virtual keys for research_agent, summarizer_agent, and orchestrator with conservative budget caps; point staging multi-agent-app at the proxy.
  • Phase 3: Validate guardrail masking, fallback behavior (simulate a Bedrock throttle), and confirm a full Langfuse trace spans all three agents.
  • Phase 4: Promote proxy and agent app to production; raise budget caps to production levels; enable alerting on /spend/logs thresholds.
  • Phase 5: Evaluate Agent Engine as an alternate deployment target once PSC-interface networking is validated against VPC Service Controls requirements.

model_list:
  - model_name: claude-sonnet
    litellm_params:
      model: bedrock/anthropic.claude-sonnet-4-6
      aws_region_name: us-east-1
  - model_name: claude-sonnet
    litellm_params:
      model: bedrock/anthropic.claude-sonnet-4-6
      aws_region_name: us-west-2
  - model_name: gemini-2.5-pro
    litellm_params:
      model: vertex_ai/gemini-2.5-pro
      vertex_project: os.environ/GCP_PROJECT_ID
      vertex_location: us-central1

router_settings:
  routing_strategy: least-busy
  fallbacks: [{"claude-sonnet": ["gemini-2.5-pro"]}]
  num_retries: 2

guardrails:
  - guardrail_name: pii-mask
    litellm_params:
      guardrail: presidio
      mode: [pre_call, post_call]
      pii_entities_config:
        PERSON: MASK
        EMAIL_ADDRESS: MASK
        PHONE_NUMBER: MASK

litellm_settings:
  success_callback: ["langfuse"]
  failure_callback: ["langfuse"]

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  database_url: os.environ/DATABASE_URL

Appendix B — Agent Code Reference

from google.adk.agents import LlmAgent
from google.adk.models.lite_llm import LiteLlm

research_agent = LlmAgent(
    name="research_agent",
    model=LiteLlm(
        model="claude-sonnet",
        api_base=os.environ["LITELLM_PROXY_URL"],
        api_key=os.environ["RESEARCH_AGENT_VIRTUAL_KEY"],
        extra_body={"metadata": {"agent_name": "research_agent"}},
    ),
    instruction="Research the topic using the search tool.",
    tools=[search_tool],
)

orchestrator = LlmAgent(
    name="orchestrator",
    model=LiteLlm(model="gemini-2.5-pro", api_base=os.environ["LITELLM_PROXY_URL"],
                  api_key=os.environ["ORCHESTRATOR_VIRTUAL_KEY"]),
    sub_agents=[research_agent, summarizer_agent],
    instruction="Delegate research, then delegate summarization.",
)
