§5.1 — DEBUG FAILURES

Debug Failures

LLM system failures are rarely "the model is bad" — they're almost always attributable to a specific pipeline stage, if you can see inside it.

A working failure taxonomy
  • Retrieval failures — the right chunk was never retrieved (embedding mismatch, poor chunking, over-aggressive metadata filter) — diagnose with retrieval-only metrics (§4.8) before blaming generation.
  • Grounding/faithfulness failures — the right context was retrieved but the model ignored it or contradicted it — a prompting or instruction-following issue, not a retrieval one.
  • Hallucination — confident, fluent, and wrong; more likely with weak grounding, ambiguous prompts, or a question genuinely outside the model's or the corpus's knowledge.
  • Tool/agent failures — wrong tool selected, malformed arguments, misinterpreted tool output, or a planning loop that never terminates — needs step-level tracing (§4.10) to isolate which hop broke.
  • Format/parsing failures — the model's output doesn't match the schema your code expects — commonly fixed with stricter structured-output constraints or output validation (§4.9), not more prompt pleading.
  • Regression after a change — a prompt, model version, or retrieval tweak that improved one case degraded another — this is exactly what golden-set regression testing (§4.8) exists to catch before users do.
A debugging method
  1. Reproduce with the traced request (§4.10) — get the exact prompt, retrieved context, and tool calls involved.
  2. Localize the failing stage — inspect retrieval output, then prompt assembly, then the raw model output, in order, rather than assuming it's "the model."
  3. Check whether it's isolated or systemic — one weird input, or does it reproduce on a class of inputs in your golden set?
  4. Form a hypothesis tied to a specific mechanism (chunking boundary, missing few-shot example, ambiguous tool description) — not "try a different prompt and see."
  5. Fix, then run full regression eval before shipping — a fix for one case can regress others.
Common trap

Jumping straight to "let's try a bigger/better model" without first checking whether the failure is actually a retrieval, chunking, or prompt problem. Model upgrades are the most expensive and least targeted fix available — they're rarely the right first move.

Self-check questions
  1. Given a wrong answer, what's the ordered sequence of pipeline stages you'd inspect to localize the cause?
  2. Why is "the model hallucinated" often an incomplete diagnosis rather than a root cause?
§5.2 — OPTIMIZE LATENCY

Optimize Latency

Attack the specific bottleneck — decode-phase token generation, retrieval, or pipeline structure each need a different fix.

Where latency actually comes from
  • Time to first token (TTFT) — dominated by prefill (§3.5) plus any retrieval/pre-processing before the model even starts generating.
  • Inter-token latency — dominated by the sequential decode loop (§3.5), which is memory-bandwidth-bound — this is why KV cache size and GPU memory bandwidth matter more here than raw compute (FLOPs).
  • Retrieval/pipeline latency — vector search, re-ranking, and any tool calls all add serial time before or after the LLM call — often invisible until you trace it (§4.10).
Levers, from cheapest to most involved
  • Streaming responses — send tokens to the user as generated rather than waiting for the full response; doesn't reduce total latency but dramatically improves perceived latency.
  • Prompt/prefix caching — reuse KV cache (§3.9) across requests sharing a system prompt or common prefix.
  • Reduce context size — tighter retrieval (§4.4), better chunking (§4.3), and trimming unnecessary history all shrink prefill cost directly.
  • Parallelize independent steps — run independent retrieval calls or tool calls concurrently instead of serially in an agent loop.
  • Smaller/quantized/distilled models — use the smallest model that meets the quality bar for a given task; quantization (§3.6) reduces memory-bandwidth pressure directly, which is the actual bottleneck in decode.
  • Speculative decoding — a small, fast "draft" model proposes several tokens ahead, which the large model verifies in a single parallel pass, accepting the ones that match — reduces the number of slow, sequential large-model steps needed.
  • Better serving infrastructure — continuous/dynamic batching, PagedAttention-style memory management (§3.9), and right-sized hardware for the workload's actual bottleneck (memory bandwidth vs. compute).
  • Task decomposition/routing — route simple requests to a smaller/faster model and reserve the largest model for genuinely hard cases.
Diagnostic habit

Before optimizing, break down where time is actually going (§4.10's latency breakdown) — teams commonly spend engineering effort speeding up the LLM call when retrieval or a serial tool-call chain is the real bottleneck.

Self-check questions
  1. Why does streaming improve perceived latency without reducing total generation time?
  2. Why is decode-phase latency bound by memory bandwidth rather than raw compute, and what does that imply about which optimizations help most?
§5.3 — REDUCE COSTS

Reduce Costs

Cost in an LLM system is a function of tokens processed and model choice — nearly every lever traces back to one of those two.

Where cost comes from
  • Input tokens — prompt + system message + retrieved context + conversation history — often the largest, most controllable cost driver in a RAG or agent system.
  • Output tokens — typically priced higher per token than input; verbose or overly long responses compound this directly.
  • Model tier — larger/frontier models cost substantially more per token than smaller ones; the question is whether the task actually needs that capability.
  • Retry/redundant calls — failed structured-output parses, agent loops that re-call the same tool, or over-eager self-consistency sampling (§4.5) all multiply cost invisibly if unmonitored.
Levers
  • Model routing / cascading — send easy requests to a cheap model, escalate to a larger model only when needed (e.g. based on a confidence signal or a cheap classifier).
  • Prompt & context trimming — tighter retrieval top-k, shorter system prompts, summarizing or truncating long conversation history instead of resending it in full every turn.
  • Prompt/prefix caching — many providers offer reduced pricing for cached prefix tokens (§3.9/§5.2) — a direct cost win, not just a latency one, when applicable.
  • Quantization & self-hosting — for high-volume workloads, a quantized open model self-hosted on right-sized hardware can undercut per-token API pricing — worth modeling against actual volume, not assumed.
  • Batching — for non-real-time workloads, batch APIs (where available) typically offer meaningfully lower per-token pricing in exchange for higher latency.
  • Caching responses — for repeated or near-duplicate queries, cache the final answer itself (not just KV cache) when semantically appropriate.
  • Output length control — explicit length constraints or format requirements (§4.5) to avoid unnecessarily verbose generations.
Common trap

Optimizing cost without evaluation (§4.8) in the loop — swapping to a cheaper model or shrinking context can quietly degrade quality below an acceptable bar. Every cost lever here needs to be checked against your golden set, not shipped on cost savings alone.

Self-check questions
  1. Why might sending every request to the largest available model be a poor default from a cost standpoint?
  2. Why does any cost-reduction change need to be paired with an evaluation check before shipping?
§5.4 — IMPROVE RELIABILITY

Improve Reliability

LLM calls fail, time out, hallucinate, and drift — reliability engineering here means designing for those failure modes as first-class, not exceptions.

Core practices
  • Retries with backoff — for transient API errors/timeouts; combined with idempotency handling so a retried agent action doesn't double-execute a side effect (e.g. don't send an email twice).
  • Timeouts & fallbacks — a hard timeout on any LLM/tool call with a defined fallback behavior (cached answer, simpler model, graceful degradation message) rather than an indefinitely hanging request.
  • Structured output validation — validate every model response against an expected schema (§4.9) before it flows further downstream; treat a validation failure as a normal, handled case, not a crash.
  • Consistency checks — for high-stakes outputs, techniques like self-consistency (§4.5) or a secondary verification pass trade cost for reliability.
  • Circuit breakers — stop routing traffic to a degraded dependency (a flaky model endpoint, a failing retrieval index) once error rates cross a threshold, instead of continuing to fail every request against it.
  • Graceful degradation — define what the system should do when a component is down: fall back to a smaller model, skip retrieval and answer from general knowledge with a caveat, or return a clear "can't answer right now" rather than a bad guess presented confidently.
  • Continuous evaluation & drift detection — quality can silently degrade even with no code changes (data distribution shifts, an underlying model provider updates a model version) — this is exactly why observability (§4.10) needs to run continuously, not just at launch.
Framing that helps

Treat the LLM call the way you'd treat any unreliable external dependency (a third-party API) in traditional systems design — because functionally, that's what it is: variable latency, occasional failures, and outputs that need validation before you trust them.

Self-check questions
  1. Why do retries on agent tool calls need idempotency handling that a simple text-generation retry doesn't?
  2. What's a concrete graceful-degradation behavior for a RAG system when the vector database is temporarily unavailable?
§5.5 — DESIGN SCALABLE SYSTEMS

Design Scalable AI Systems

Bringing it all together — the architectural decisions that let a system handle real traffic without falling over on cost, latency, or quality.

System design considerations
  • Stateless request handling + externalized state — keep conversation/session state in a database or cache rather than in-process, so any request can be served by any instance — standard horizontal-scaling practice, still true here.
  • Async / queue-based processing — for non-interactive or long-running agent tasks, decouple request intake from processing with a queue, so traffic spikes don't directly translate to LLM provider rate-limit failures.
  • Rate limit & quota management — model provider rate limits are a real capacity constraint; design for graceful queuing/backpressure rather than assuming unlimited throughput.
  • Caching layers — response caching, prompt/prefix caching (§3.9), and retrieval result caching each address a different repeated-work pattern at scale.
  • Load balancing across models/providers — routing traffic across multiple model deployments or even providers for both throughput and resilience against a single provider's outage.
  • Horizontal scaling of retrieval infrastructure — sharding/replicating the vector database (§4.2) as corpus size and query volume grow, independent of how the LLM-serving layer scales.
  • Multi-tenancy considerations — isolating data, rate limits, and cost attribution per tenant/customer in a shared system, including making sure retrieval respects per-tenant access permissions.
  • Capacity planning — modeling expected concurrent requests against KV cache memory limits (§3.9) and provider rate limits, not just against raw compute — this is frequently the real ceiling on how many concurrent users a deployment can serve.
The synthesis

A scalable AI system design pulls directly from every earlier stage: KV cache and quantization (Stage 3) bound how many concurrent requests one GPU can serve; retrieval and vector database design (Stage 4) bound how the knowledge layer scales independently; evaluation and observability (Stage 4) are what let you scale safely — catching quality regressions before they reach all your users rather than after.

Self-check questions
  1. Why does capacity planning for an LLM-serving system need to account for KV cache memory, not just raw GPU compute?
  2. Why should conversation state live outside the serving process in a horizontally scaled deployment?
  3. Design prompt: sketch, at a high level, how you'd scale a RAG-based support assistant from 10 to 10,000 concurrent users — which components scale independently, and where would you expect the first bottleneck to appear?
