STAGE 04

Learn AI Engineering

§4.1 — RAG

Retrieval-Augmented Generation

Ground the model in your data at inference time, instead of trying to bake every fact into its weights.

RAG retrieves relevant passages from an external knowledge source and inserts them into the prompt before generation, so the model answers using supplied evidence rather than relying solely on what it memorized during training.

The core pipeline
  • Ingest — source documents are cleaned, chunked (§4.3), and embedded (§3.2).
  • Index — embeddings are stored in a vector database (§4.2) alongside metadata.
  • Retrieve — the user's query is embedded and used to find the most relevant chunks (§4.4).
  • Augment — retrieved chunks are inserted into the prompt, usually with instructions to answer only from the provided context.
  • Generate — the LLM produces an answer grounded in the retrieved evidence, ideally with citations back to source chunks.
Why RAG over fine-tuning for knowledge
  • Knowledge updates instantly (edit the source, re-index) instead of requiring retraining.
  • Answers can cite sources, which fine-tuned "memorized" knowledge cannot.
  • Reduces (but does not eliminate) hallucination by grounding generation in retrieved text.
  • Fine-tuning is better suited to teaching style, format, or task behavior — not injecting fast-changing facts.
Common trap

RAG is not automatically accurate — a model can still hallucinate even with correct context in front of it, or ignore the retrieved evidence entirely if the prompt doesn't clearly instruct it to prioritize that context. RAG reduces hallucination risk; it doesn't remove it, which is exactly why Evaluation (§4.8) and Guardrails (§4.9) still matter downstream of a working retrieval pipeline.

Self-check questions
  1. Why does RAG generally beat fine-tuning for keeping a model current on fast-changing facts?
  2. What can still go wrong even when retrieval returns the correct passage?
§4.2 — VECTOR DATABASES

Vector Databases

Storage and search built for "find things that mean something similar," not "find things that match exactly."

A vector database stores embeddings (§3.2) and answers approximate nearest neighbor (ANN) queries efficiently — given a query vector, return the most similar stored vectors — at a scale where brute-force comparison against every stored vector would be too slow.

Core concepts
  • Similarity metrics — cosine similarity, dot product, or Euclidean (L2) distance — the choice should match how the embedding model was trained/normalized.
  • ANN indexing algorithms — HNSW (hierarchical navigable small world graphs) is the dominant choice for high recall/speed trade-offs; IVF (inverted file index) partitions space into clusters searched selectively; both trade a little accuracy for large speed gains over brute force.
  • Metadata filtering — combining vector similarity with structured filters (e.g. date range, document type, permission tags) — critical for real applications, not just a nice-to-have.
  • Hybrid search — combining dense vector similarity with sparse keyword search (e.g. BM25) to catch cases pure semantic search misses, like exact product codes or acronyms.
  • Index rebuild / freshness — how new or updated documents get into the index, and the latency between a source update and it being retrievable.

Why it matters downstream

Index choice and metadata filtering design directly affect both retrieval quality (§4.4) and production latency/cost (Stage 5) — an over-large index with no filtering searched on every query is a classic avoidable latency and cost problem.

Self-check questions
  1. Why do ANN algorithms trade a small amount of accuracy for large speed gains, and why is that usually the right trade-off?
  2. When would you reach for hybrid search instead of pure vector similarity?
§4.3 — CHUNKING

Chunking

How you split documents before embedding them — an unglamorous decision that quietly determines most of a RAG system's real-world quality.

Strategies
  • Fixed-size chunking — split every N tokens (§3.1), often with overlap between chunks so context isn't lost at a boundary. Simple, but can cut sentences or ideas in half.
  • Recursive / structure-aware chunking — split along natural boundaries first (sections, paragraphs, sentences), falling back to smaller units only when a piece is still too large.
  • Semantic chunking — use embedding similarity between adjacent sentences to detect topic shifts and split there, rather than at an arbitrary size.
  • Document-aware chunking — respect structural elements specifically — Markdown headers, table boundaries, code blocks — so a chunk doesn't split a table row from its header.
  • Chunk overlap — repeating some tokens between consecutive chunks so information spanning a boundary is still retrievable from at least one chunk.
  • Chunk size trade-off — smaller chunks → more precise retrieval but less surrounding context per chunk; larger chunks → more context but noisier matches and fewer chunks fit in the context window (§3.8).
Common trap

Using one fixed chunk size and overlap for every document type in a corpus is a frequent source of silently poor retrieval — a legal contract, a chat log, and an API reference doc have very different natural structure and need different chunking strategies to retrieve well.

Self-check questions
  1. Why does chunk size trade off retrieval precision against available context?
  2. Why might semantic chunking outperform fixed-size chunking on a long, topic-shifting document?
§4.4 — RETRIEVAL

Retrieval

Finding and ranking the right evidence — the step that most directly determines whether the model has a chance of answering correctly.

Core techniques
  • Dense retrieval — embedding-based semantic similarity search (§4.2), good at capturing meaning/paraphrase.
  • Sparse retrieval (BM25/keyword) — classic term-frequency-based search, strong on exact terms, codes, names, rare tokens dense retrieval can miss.
  • Hybrid retrieval — combine both, typically merged via reciprocal rank fusion or a weighted score.
  • Re-ranking — a second, more expensive but more accurate model (often a cross-encoder) re-scores an initial candidate set (from a fast first-pass retriever) to improve final ranking quality before the top few go into the prompt.
  • Query transformation — rewriting the user's query before retrieval, e.g. HyDE (generating a hypothetical answer and embedding that instead of the raw question), query expansion, or decomposing a complex question into sub-queries.
  • Multi-hop retrieval — when an answer requires combining evidence from multiple documents, retrieving iteratively based on partial reasoning rather than in a single pass.
  • Top-k selection — how many chunks to actually pass into the prompt, balancing coverage against context window budget (§3.8) and the "lost in the middle" effect.
Why it matters downstream

Retrieval quality is usually the single highest-leverage place to improve a RAG system's accuracy — teams often over-invest in prompt tweaking when the real problem is that the right chunk was never retrieved in the first place. This is exactly what retrieval-focused evaluation metrics (§4.8) are built to catch.

Self-check questions
  1. Why does a two-stage "retrieve broadly, then re-rank" pipeline often outperform retrieving top-k directly from the vector index?
  2. When would sparse (keyword) retrieval catch something dense retrieval misses?
§4.5 — PROMPT ENGINEERING

Prompt Engineering

The cheapest, fastest lever for changing model behavior — try this before reaching for RAG or fine-tuning.

Core techniques
  • Zero-shot / few-shot prompting — asking directly, versus providing a handful of worked examples in the prompt to demonstrate the desired format or reasoning pattern.
  • Chain-of-thought (CoT) — instructing (or demonstrating via examples) the model to reason step by step before giving a final answer, which measurably improves performance on multi-step reasoning tasks.
  • System vs. user vs. assistant roles — the system message sets persistent behavior/constraints; separating instructions from user-provided content also helps reduce prompt injection risk (§4.9).
  • Structured output prompting — instructing (and often constraining via the API) the model to return JSON or another fixed schema, essential for programmatic downstream use.
  • Instruction clarity & specificity — explicit format, length, tone, and constraints outperform vague asks; positive instructions ("do X") are generally more reliable than only negative ones ("don't do Y").
  • Self-consistency — sampling multiple reasoning paths and taking the majority answer, trading extra inference cost for higher accuracy on hard reasoning tasks.
Common trap

Prompt engineering is often treated as a substitute for fixing a genuinely missing capability or missing information. If the model doesn't have the facts (use RAG) or the underlying skill (consider fine-tuning), no amount of prompt wording will reliably fix it — prompting shapes behavior on top of existing knowledge and capability, it doesn't add either.

Self-check questions
  1. Why does chain-of-thought prompting tend to help on multi-step reasoning tasks specifically?
  2. Why separate system instructions from user content, beyond just organization?
§4.6 — AI AGENTS

AI Agents

Moving from "generate one answer" to "take actions, observe results, and decide what to do next."

An agent wraps an LLM in a loop: the model decides which tool to call (if any), the tool executes, the result is fed back in, and the model decides the next step — repeated until the task is complete or a stopping condition is hit.

Core concepts
  • Tool / function calling — the model is given a set of available tool definitions (name, description, parameter schema) and outputs a structured call when it decides one is needed; the calling application executes it and returns the result.
  • ReAct pattern (Reason + Act) — the model interleaves explicit reasoning ("thought") with actions ("tool call") and observations, in a loop — one of the most common agent-loop formulations.
  • Planning — decomposing a complex goal into an ordered sequence of steps, either upfront or dynamically as new information arrives.
  • Memory — short-term (conversation/scratchpad within a session) versus long-term (persisted across sessions, often backed by a vector store or database) state the agent can draw on.
  • Multi-agent systems — multiple specialized agents (e.g. a planner, a researcher, a coder) coordinating on a task, communicating through defined interfaces or a shared orchestrator.
  • Termination / stopping conditions — max iterations, a explicit "done" signal from the model, or a validation check — necessary because an agent loop can otherwise run indefinitely or loop unproductively.
Common trap

Agent loops fail silently in production far more than single-turn LLM calls: a tool call with a subtly wrong argument, a misinterpreted tool result, or a planning loop that never converges. This is why Observability (§4.10) and hard iteration/cost limits matter especially for agentic systems.

Self-check questions
  1. What's the core loop that turns a single LLM call into an "agent"?
  2. Why do agent systems need explicit stopping conditions that a single-turn prompt doesn't?
§4.7 — MCP

Model Context Protocol (MCP)

A standard interface between models/agents and the tools, data sources, and apps they need to act on — instead of a custom integration per model per tool.

Before a shared standard, connecting an agent to N tools across M different model providers meant roughly N×M bespoke integrations. MCP defines a common protocol so a tool (or data source) implements one MCP server once, and any MCP-compatible client (agent framework, chat app) can discover and use it — the same "write once, connect anywhere" motivation behind protocols like LSP in developer tooling.

Core concepts
  • MCP server — exposes a specific tool's or data source's capabilities (e.g. "search Jira issues," "query this database") in the standard protocol format.
  • MCP client — the agent/host application that connects to one or more MCP servers and makes their capabilities available to the model.
  • Resources — read-only data an MCP server exposes (e.g. a file, a database record) that a model can pull into context.
  • Tools — actions an MCP server exposes that the model can invoke, analogous to function calling (§4.6) but standardized across providers and hosts.
  • Prompts — reusable, server-defined prompt templates a client can surface to users or inject into a conversation.
  • Transport — the underlying connection (e.g. stdio for local processes, HTTP/SSE for remote servers) MCP messages travel over.
Why it matters downstream

MCP is what turns "AI agent" from a bespoke, per-project integration effort into something composable — an organization can build one internal MCP server for its knowledge base or ticketing system, and every agent/tool that speaks MCP gets access, without a new custom integration each time.

Self-check questions
  1. What integration problem does a standard protocol like MCP solve that ad hoc function calling per provider doesn't?
  2. What's the difference between an MCP "resource" and an MCP "tool"?
§4.8 — EVALUATION

Evaluation

Without systematic evaluation, "we improved the prompt/retrieval/model" is just a guess.

Core approaches
  • Golden datasets — a curated set of representative inputs with known-good expected outputs (or grading criteria), used consistently across changes so results are comparable over time.
  • Reference-based metrics — BLEU/ROUGE (n-gram overlap, mostly legacy for LLM eval), exact match, semantic similarity to a reference answer — useful when there's a clear "correct" answer.
  • LLM-as-judge — using a strong LLM to score or compare outputs against a rubric, useful for open-ended quality where no single reference answer exists; needs its own validation against human judgment to trust.
  • Human evaluation — the ground truth for subjective quality, but slow and expensive; often used to spot-check and calibrate automated methods rather than run continuously.
  • RAG-specific metrics — retrieval precision/recall (did we retrieve the right chunks), faithfulness/groundedness (is the answer actually supported by the retrieved context), answer relevance (does it address the question).
  • Task-specific metrics — exact-match accuracy for classification-like tasks, pass@k for code generation, and so on — the right metric follows from the task, not a one-size-fits-all number.
  • Regression testing — re-running the golden set on every meaningful prompt, model, or retrieval change to catch quality regressions before they reach users.
Why it matters downstream

Evaluation is the feedback loop for everything else in this stage — without it you can't tell whether a chunking change, a re-ranker, or a new prompt actually helped, and you can't detect silent quality regressions in production (Stage 5).

Self-check questions
  1. Why is "faithfulness" a distinct metric from "answer relevance" in RAG evaluation — what failure mode does each catch on its own?
  2. Why does LLM-as-judge need its own validation against human judgment before you trust it?
§4.9 — GUARDRAILS

Guardrails

Constraints and checks around a model's inputs and outputs — because prompting alone doesn't reliably guarantee safe or on-scope behavior.

Core concepts
  • Input validation / filtering — checking user input before it reaches the model — scope checks, PII detection, blocking known attack patterns.
  • Prompt injection defense — protecting against instructions hidden in retrieved documents, tool outputs, or user input that try to override the system's intended behavior; mitigations include strict role separation, treating retrieved/tool content as data rather than instructions, and output-side validation.
  • Output validation — checking the model's response before it's shown to the user or used downstream — schema validation for structured output, toxicity/safety classifiers, fact-checking against retrieved sources.
  • Topic/scope restriction — keeping a domain-specific assistant from answering (or acting) far outside its intended purpose.
  • PII & sensitive data handling — detecting and redacting or blocking personal or confidential information in both directions (input and output).
  • Rate limiting & abuse prevention — protecting against automated misuse of an agent's tool-calling capability in particular, where a single successful jailbreak could trigger a real-world action, not just a bad text response.
Common trap

Treating "the system prompt says not to do X" as sufficient protection. System prompt instructions are a strong nudge, not an enforcement mechanism — a determined adversarial input (especially injected through retrieved content or tool output the model treats as trustworthy) can override them. Real guardrails validate independently of what the model was merely told to do.

Self-check questions
  1. Why is a system-prompt instruction alone not sufficient as a security guardrail?
  2. Why does an agent with tool access need stricter guardrails than a plain chat model?
§4.10 — OBSERVABILITY

Observability

You can't fix — or even find — what you can't see. LLM systems fail in ways traditional monitoring wasn't built to catch.

Core concepts
  • Tracing — capturing the full path of a request through a multi-step pipeline (retrieval → re-rank → prompt assembly → LLM call → tool calls → final output), essential for debugging agentic and RAG systems where the LLM call is just one step among many.
  • Logging prompts & completions — retaining the actual inputs and outputs (with appropriate privacy handling) needed to reproduce and diagnose a specific failure after the fact.
  • Token & cost tracking — per-request and aggregate visibility into token usage and spend, broken down by model, feature, or customer — directly feeds Stage 5 cost work.
  • Latency breakdown — measuring time spent in each pipeline stage (retrieval, prefill, decode, tool calls) separately, since "the LLM call is slow" and "retrieval is slow" call for completely different fixes.
  • Quality/drift monitoring — tracking evaluation metrics (§4.8) or proxy signals (user feedback, thumbs up/down, escalation rate) continuously in production, not just at release time, since data distribution and user behavior shift over time.
  • Alerting — thresholds on error rate, latency, cost, or quality signals that page a human before a slow degradation becomes a major incident.
Why it matters downstream

Observability is the connective tissue for all of Stage 5 — you cannot debug failures, optimize latency, reduce costs, or improve reliability in a system you can't see inside of at the level of individual pipeline steps.

Self-check questions
  1. Why does a multi-step RAG/agent pipeline need tracing in a way a single LLM API call doesn't as urgently?
  2. Why is quality monitoring something you need continuously in production, not just at initial release?
