STAGE 03

Understand LLMs deeply

Follow one request through the whole pipeline: text is cut into tokens → tokens become vectors → position is injected → the transformer is trained on all of it → at inference time it generates one token at a time, cached and (often) quantized and (sometimes) sparsely routed, bounded by a context window.

§3.1 — TOKENIZATION

Tokenization

The first thing that happens to any text — and a source of more downstream weirdness than people expect.

A tokenizer splits raw text into a fixed vocabulary of tokens — not quite words, not quite characters. Modern LLMs use subword tokenization so that any string can be represented (rare words split into pieces; common words stay whole), keeping the vocabulary a manageable size (commonly 30K–150K+ tokens) while still handling arbitrary text.

Core concepts
  • Byte-Pair Encoding (BPE) — iteratively merges the most frequent adjacent symbol pairs, starting from characters/bytes, to build a vocabulary. Used by GPT-family models.
  • WordPiece / SentencePiece / Unigram — alternative subword algorithms with similar goals, different merge/selection criteria (used by BERT, T5, Llama respectively, roughly).
  • Vocabulary size — a trade-off: larger vocab → shorter sequences per input but a bigger embedding/output matrix and more parameters spent there.
  • Special tokens — reserved tokens like <bos>, <eos>, <pad>, and chat-format tokens marking roles (system/user/assistant) in instruction-tuned models.
  • Token ≠ word — "unbelievable" might split into "un", "believ", "able"; a single emoji or unusual Unicode string can burn several tokens.
Common trap

Tokenization explains several "dumb" LLM failures: struggling with letter-counting or reversing a string (the model never sees individual characters, only token IDs), inconsistent behavior across languages (tokenizers trained mostly on English text produce far more tokens per non-English sentence, quietly inflating cost and eating into context budget), and odd arithmetic errors (numbers get tokenized inconsistently, e.g. "1234" vs "12" + "34").

Why it matters downstream

Every cost and limit you'll deal with in production is denominated in tokens, not words or characters: API pricing, context window limits, rate limits. Chunking strategy in RAG (Stage 4) has to account for tokenizer behavior, not raw character counts.

Self-check questions
  1. Why do subword tokenizers handle out-of-vocabulary words better than whole-word tokenizers?
  2. Why might the same sentence cost noticeably more tokens in one language than another?
  3. Why can LLMs struggle at tasks like reversing a string, given how tokenization works?
§3.2 — EMBEDDINGS

Embeddings

Turning a discrete token ID into a dense vector that captures meaning — the bridge between symbols and the geometry a neural network operates on.

An embedding layer is a lookup table: each token ID maps to a learned vector (typically hundreds to a few thousand dimensions). Through training, tokens that behave similarly in context end up with similar vectors — meaning becomes geometry, where relationships between concepts become directions and distances in vector space.

Core concepts
  • Token embeddings — the learned lookup table mapping each vocabulary entry to a vector; trained jointly with the rest of the model.
  • Contextual vs. static embeddings — older models (word2vec, GloVe) gave one fixed vector per word regardless of context; transformer-based embeddings are contextual — "bank" gets a different vector in "river bank" vs. "bank account" because attention mixes in surrounding context.
  • Embedding dimension — a capacity/cost trade-off; larger dimension can encode more nuance but costs more compute and memory throughout the model.
  • Cosine similarity — the standard way to compare two embeddings' semantic closeness, independent of vector magnitude (§1.1).
  • Sentence/document embeddings — pooling (often mean-pooling or using a dedicated embedding model) token-level vectors into one vector representing a whole passage — the backbone of semantic search and RAG retrieval (Stage 4).
  • Weight tying — many models reuse the same matrix for the input token embedding and the final output projection (logits), saving parameters.
Why it matters downstream

Embeddings are the entire foundation of vector databases and retrieval (Stage 4) — a RAG system's quality is bounded by how good its embedding model is at placing semantically related text near each other in vector space.

Self-check questions
  1. Why are transformer embeddings "contextual" while word2vec embeddings are not?
  2. Why is cosine similarity generally preferred over Euclidean distance for comparing text embeddings?
  3. What's the practical difference between a token embedding and a sentence/document embedding used for retrieval?
§3.3 — POSITIONAL ENCODING

Positional Encoding

Attention has no built-in sense of order — "the dog bit the man" and "the man bit the dog" would look identical without this.

Self-attention treats input as a set, not a sequence — it's permutation-invariant by construction. Positional encoding injects information about each token's position so the model can distinguish order.

Approaches
  • Sinusoidal (absolute) encoding — the original Transformer paper's approach: fixed sine/cosine functions of position added to the token embedding, at different frequencies per dimension. Not learned; generalizes somewhat to unseen sequence lengths.
  • Learned absolute embeddings — a trainable position embedding table, added to token embeddings (used by early GPT models). Doesn't extrapolate well past the trained max length.
  • Relative positional encoding — encodes the distance between tokens rather than their absolute position, more naturally generalizing to varying sequence lengths.
  • RoPE (Rotary Position Embedding) — the dominant modern approach (Llama, Mistral, most current open models): rotates the Query/Key vectors by an angle proportional to position, so the dot product between two tokens naturally encodes their relative distance. Widely used because it extrapolates and extends to longer contexts better than absolute schemes.
  • ALiBi — adds a distance-proportional penalty directly to attention scores instead of modifying embeddings; another strong approach for length extrapolation.
Why it matters downstream

Positional encoding choice directly determines how well a model extends beyond its trained context length — RoPE scaling tricks (like position interpolation or NTK-aware scaling) are exactly how many "extended context" model variants are produced without full retraining.

Self-check questions
  1. Why is self-attention permutation-invariant without positional encoding?
  2. Why do relative encodings like RoPE generally extrapolate to longer sequences better than learned absolute position embeddings?
§3.4 — TRAINING & FINE-TUNING

Training & Fine-tuning

From a randomly initialized transformer to a model that follows instructions safely — three stages, each with a different objective.

The three-stage pipeline
  • 1. Pretraining — self-supervised next-token prediction over a massive text corpus. No labels needed — the "label" for each position is just the next real token. This is where the bulk of compute and cost goes, and where the model acquires broad language and world knowledge.
  • 2. Supervised Fine-Tuning (SFT) — further training on a smaller, curated set of high-quality instruction–response pairs, teaching the base model to follow instructions and hold a conversation format rather than just continue text.
  • 3. Alignment (RLHF / DPO) — RLHF trains a reward model on human preference comparisons, then uses reinforcement learning (commonly PPO) to optimize the LLM against that reward, with a KL-divergence penalty (§1.2) keeping it from drifting too far from the SFT model. DPO (Direct Preference Optimization) is a newer, simpler alternative that optimizes directly on preference pairs without a separate reward model or RL loop.
Efficient fine-tuning
  • Full fine-tuning — updates every parameter; most capable but expensive in compute and memory (needs to store optimizer state for the whole model).
  • LoRA (Low-Rank Adaptation) — freezes the original weights and injects small trainable low-rank matrices (§1.1) alongside them; drastically cuts trainable parameters and memory while approximating full fine-tuning's effect for many tasks.
  • QLoRA — LoRA on top of a quantized (§3.6) base model, pushing fine-tuning onto much smaller hardware.
  • Adapters / prefix-tuning — other parameter-efficient fine-tuning (PEFT) families: small inserted modules or learned prompt-like vectors, base model frozen.
  • Catastrophic forgetting — fine-tuning too aggressively on a narrow task can degrade the model's general capabilities; a key reason PEFT methods and careful learning rates matter.
Scale intuition
Loss ≈ scales predictably with model size, data size, and compute — "scaling laws" (Chinchilla, Kaplan et al.) are why frontier labs plan pretraining runs quantitatively rather than by trial and error
Why it matters downstream

Whether to prompt-engineer, RAG, or fine-tune is one of the most common real-world engineering decisions (Stage 4/5) — and it hinges on understanding what each training stage actually changes in the model versus what retrieval or prompting can substitute for at inference time, more cheaply.

Self-check questions
  1. What's the practical difference between what pretraining teaches a model and what SFT teaches it?
  2. Why does RLHF use a KL penalty against the reference model instead of letting the policy optimize the reward freely?
  3. Why does LoRA use low-rank matrices specifically — what assumption about fine-tuning updates does that rely on (tie back to §1.1)?
  4. When would you reach for fine-tuning instead of RAG or better prompting?
§3.5 — INFERENCE

Inference

Generation is autoregressive: one token out, fed back in as input, repeated — which is exactly why it's slow and why so much engineering exists to speed it up.

Core mechanics
  • Autoregressive generation — the model predicts a probability distribution over the next token, a token is selected, appended to the sequence, and the whole (now longer) sequence is fed back in to predict the next one — repeated until an end token or length limit.
  • Prefill vs. decode — prefill processes the entire input prompt in one parallel forward pass (fast, compute-bound); decode generates output tokens one at a time (slow, memory-bandwidth-bound) — this split is central to understanding inference latency and cost (Stage 5).
Sampling strategies
  • Greedy decoding — always pick the single highest-probability token; deterministic but repetitive and can get stuck in loops.
  • Temperature — rescales logits before softmax; lower = more confident/deterministic, higher = flatter distribution, more random/creative.
  • Top-k sampling — restrict sampling to the k highest-probability tokens.
  • Top-p (nucleus) sampling — restrict sampling to the smallest set of tokens whose cumulative probability exceeds p; adapts the candidate pool size to how confident the distribution is.
  • Beam search — tracks several candidate sequences in parallel, keeping the most probable overall sequence; common in translation, less common for open-ended chat generation.
  • Repetition / frequency penalties — discourage the model from reusing tokens it has already generated.
Why it matters downstream

Latency in a production system is dominated by the sequential, one-token-at-a-time decode phase — this is precisely the problem that KV caching (§3.9), quantization (§3.6), and speculative decoding all attack from different angles (tie-in to Stage 5's latency work).

Self-check questions
  1. Why is the prefill phase much faster per-token than the decode phase?
  2. What's the practical difference between top-k and top-p sampling?
  3. Why would greedy decoding alone tend to produce repetitive output?
§3.6 — QUANTIZATION

Quantization

Shrinking the numbers that make up a model's weights, trading a little precision for large gains in memory and speed.

Model weights are normally stored as 32- or 16-bit floating point numbers. Quantization maps them to lower-precision formats — 8-bit, 4-bit, even lower — cutting memory footprint roughly in proportion and often speeding up inference, since moving less data is frequently the actual bottleneck (§3.5's decode phase is memory-bandwidth-bound).

Core concepts
  • Precision formats — FP32, FP16, BF16 (full/half precision, used in training), INT8, INT4 (common inference quantization targets).
  • Post-training quantization (PTQ) — quantize an already-trained model's weights, no retraining required; fast and simple, some accuracy loss.
  • Quantization-aware training (QAT) — simulate quantization effects during training so the model adapts to lower precision; better final accuracy, more expensive.
  • Per-tensor vs. per-channel quantization — whether one scale factor covers an entire weight tensor or each channel gets its own, trading simplicity for accuracy.
  • GPTQ / AWQ / GGUF — popular practical quantization methods/formats in the open-model ecosystem, each with different accuracy/speed trade-offs and tooling support.
  • Calibration — using a small representative dataset to choose good scale/zero-point values when quantizing, minimizing accuracy loss.
Common trap

Quantization isn't free — going too aggressive (e.g. naive 4-bit on a poorly calibrated model) can visibly degrade reasoning quality and increase hallucination rate. It needs to be evaluated on your actual task, not assumed safe because a benchmark number looked fine.

Why it matters downstream

Quantization is one of the primary levers for cost and latency reduction in production (Stage 5) — it's often the difference between needing an expensive multi-GPU deployment and fitting a model on a single, cheaper accelerator.

Self-check questions
  1. Why does quantization often speed up inference even though the math itself isn't fundamentally faster at low precision?
  2. What's the trade-off between post-training quantization and quantization-aware training?
  3. Why might per-channel quantization preserve accuracy better than per-tensor?
§3.7 — MIXTURE OF EXPERTS (MOE)

Mixture of Experts (MoE)

More total parameters, without paying for all of them on every forward pass.

In a standard transformer, every token passes through the same dense FFN. In an MoE model, the FFN is replaced with several parallel "expert" FFNs plus a small learned router that selects a small subset of experts (commonly 1–2 of 8 or more) to process each token — so the model has a much larger total parameter count but only "activates" a fraction of it per token.

Core concepts
  • Experts — independent FFN sub-networks, each with its own weights; typically only the attention layers remain fully shared/dense.
  • Router / gating network — a small learned layer that scores experts per token and picks the top-k to activate.
  • Sparse activation — only the selected experts' weights are used for a given token, so inference compute scales with active parameters, not total parameters.
  • Load balancing — without an auxiliary loss encouraging even usage, routers tend to collapse onto a few favorite experts, wasting capacity; load-balancing losses counteract this.
  • Total vs. active parameters — the key spec to look for in MoE model cards (e.g. "47B total, 13B active") — active parameters roughly predict inference cost/speed; total parameters roughly predict capability and memory footprint.
Why it matters downstream

MoE lets frontier labs scale total model capacity without a proportional increase in inference cost — but it does increase memory requirements (you must hold all experts in memory even if only a few run per token), which matters directly for deployment planning in Stage 5.

Self-check questions
  1. Why can an MoE model have far more total parameters than a dense model of similar inference cost?
  2. What problem does a load-balancing loss solve in MoE training?
  3. Why does MoE reduce compute cost but not necessarily memory cost?
§3.8 — CONTEXT WINDOWS

Context Windows

The maximum number of tokens a model can consider at once — a hard ceiling on how much it can "see" of a conversation or document.

Core concepts
  • Context window / context length — the total token budget shared by the prompt (input) and the generated response combined, in most API accounting.
  • Why it's bounded — attention's compute and memory cost grows roughly quadratically with sequence length (§2.4), and positional encoding schemes have to be designed or extended to support the target length (§3.3).
  • "Lost in the middle" — empirically, models often attend less reliably to information placed in the middle of a very long context than to the beginning or end — a real, measurable limitation, not just a theoretical one.
  • Long-context extension techniques — RoPE scaling/interpolation, sliding-window attention, and architectural tricks let models trained at one length serve much longer effective contexts, generally with some quality trade-off.
  • Context window vs. effective context — a model may technically accept 200K tokens while its reliable recall and reasoning quality noticeably degrades well before that limit — the advertised number and the usable number are not the same thing.
Why it matters downstream

Context window size directly shapes RAG design (Stage 4): how many chunks you can retrieve and pass in, how you order retrieved evidence to fight "lost in the middle," and it's a first-order driver of both latency and cost (Stage 5) since cost typically scales with tokens processed.

Self-check questions
  1. Why does attention's cost structure limit how large a context window can practically be?
  2. What does "lost in the middle" imply about where you should place the most important retrieved evidence in a RAG prompt?
  3. Why might a model's effective usable context be smaller than its advertised maximum?
§3.9 — KV CACHE

KV Cache

The single biggest practical speedup in autoregressive generation: stop recomputing what you already computed.

During decode (§3.5), generating each new token technically requires attention over every previous token. Without caching, that means recomputing the Key and Value projections (§2.4) for the entire sequence so far, at every single generation step — wildly redundant, since those K/V vectors for past tokens never change. The KV cache stores them once and reuses them, so each new step only computes K/V for the one new token.

Core concepts
  • What's cached — the Key and Value projections for every token processed so far, per layer, per attention head. Not the Query — a fresh Query is only needed for the current token.
  • Memory cost — grows linearly with sequence length and batch size, and scales with number of layers, heads, and head dimension; at long context lengths and large batch sizes, KV cache memory — not model weights — often becomes the dominant memory consumer on the serving GPU.
  • Multi-Query Attention (MQA) / Grouped-Query Attention (GQA) — reduce KV cache size by sharing Key/Value projections across multiple (or all) attention heads instead of giving every head its own — a major lever for serving efficiency, used in most modern production LLMs.
  • PagedAttention — a memory-management technique (popularized by vLLM) that manages the KV cache in fixed-size non-contiguous blocks (like OS virtual memory paging), dramatically reducing memory fragmentation/waste and enabling much higher serving throughput.
  • Prefix / prompt caching — when multiple requests share a common prefix (e.g. the same system prompt), the KV cache for that shared prefix can be computed once and reused across requests, cutting both latency and cost.
Common trap

People assume GPU memory limits are mostly about the model's weights. In real serving conditions with long contexts and many concurrent users, the KV cache frequently dominates memory usage — which is exactly why GQA/MQA and PagedAttention exist and why "max concurrent requests" is often capped by KV cache capacity, not compute.

Why it matters downstream

This is one of the most direct through-lines into Stage 5: KV cache size drives GPU memory planning, batch size limits, and thus throughput and cost per request — a core lever production engineers pull when optimizing latency and reducing serving costs.

Self-check questions
  1. Why doesn't the Query vector need to be cached the way Keys and Values do?
  2. How does GQA reduce KV cache memory, and what's the trade-off versus full multi-head attention?
  3. Why can prompt/prefix caching meaningfully cut latency for applications with a shared system prompt?
