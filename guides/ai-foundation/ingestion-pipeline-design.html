5.2

Intake — how files actually arrive

Two distinct flows; they have different failure modes and different tooling.

Flow A — one-time bulk migration (thousands of existing PDFs), via Storage Transfer Service.

gsutil rsync is the wrong tool at this volume — it has no built-in retry orchestration, no metadata preservation, and turns every failure into a manual investigation. Storage Transfer Service (STS) is Google's purpose-built migration tool for exactly this case (on-prem file share → Cloud Storage, thousands to millions of files) and should be used instead:

  1. Confirm the source of truth from Open Decision #9 (file share, SharePoint library, local drives, existing DMS)
  2. For a file share/NAS: provision a Linux host (agents aren't supported directly on Windows — mount via a Linux VM if the share is Windows-hosted) with the source directory mounted; restrict the mount to only the directory tree being migrated, never the whole filesystem
  3. Grant the agent account roles/storagetransfer.user; run gcloud transfer authorize to inspect and grant exactly the required permissions rather than guessing
  4. Create an agent pool (gcloud transfer agent-pools create) and run the agent container (docker run ... gcr.io/cloud-ingest/tsop-agent) on the host
  5. Create a transfer job: source = the POSIX path on the mounted share, destination = gs://{project}-rag-pdf-raw/incoming/, with source metadata preservation enabled, scheduled to run outside business hours to avoid network congestion
  6. STS handles retry, partial-failure tracking, and incremental re-runs natively — a failed transfer operation is visible in Cloud Logging and re-runnable without a custom manifest/retry system
  7. For SharePoint: STS does not speak the SharePoint API. Use the Graph API to extract into a staging area, then STS or direct upload from there into incoming/
Gap STS doesn't close

Filesystem metadata (timestamps, path) isn't the same as the citation fields required (owner, classification — Section 6.1.1). This needs a separate migration manifest — a path→owner→classification mapping sourced from Open Decision #8's system of record — applied as a post-transfer step that sets GCS custom object metadata before validation (5.3) runs. Scope this as real, explicit work; it does not fall out of the transfer automatically.

Flow B — ongoing intake (new documents after go-live).

  • A designated upload path (either a lightweight internal upload UI, or the same STS job re-run on a recurring incremental schedule against the source system) writes new PDFs to the same incoming/ prefix
  • Same metadata requirement applies — no PDF enters the pipeline without owner/classification set at upload

Both flows land in the same bucket/prefix so the rest of the pipeline doesn't need to know which flow a file came from.

5.3

Validation & deduplication

Triggered by Eventarc on google.cloud.storage.object.v1.finalized for the incoming/ prefix.

ingestion/intake_validator.py 
import hashlib
from google.cloud import storage, firestore

def validate_and_dedup(bucket_name: str, object_name: str) -> dict:
    client = storage.Client()
    blob = client.bucket(bucket_name).blob(object_name)
    blob.reload()

    # 1. File type / size checks
    if blob.content_type != "application/pdf":
        return _reject(object_name, "not_pdf")
    if blob.size == 0 or blob.size > 200 * 1024 * 1024:  # 200MB ceiling
        return _reject(object_name, f"invalid_size:{blob.size}")

    # 2. Content hash for dedup (not filename — filenames lie)
    content_hash = hashlib.sha256(blob.download_as_bytes()).hexdigest()

    db = firestore.Client()
    existing = db.collection("ingested_documents").document(content_hash).get()
    if existing.exists:
        return _reject(object_name, f"duplicate_of:{existing.get('object_name')}")

    # 3. Required metadata present?
    metadata = blob.metadata or {}
    required = {"owner", "classification"}
    missing = required - metadata.keys()
    if missing:
        return _reject(object_name, f"missing_metadata:{missing}")

    # 4. Record and move to staging
    db.collection("ingested_documents").document(content_hash).set({
        "object_name": object_name,
        "status": "validated",
        "metadata": metadata,
    })
    _move_to_staging(bucket_name, object_name)
    return {"status": "validated", "hash": content_hash}

def _reject(object_name: str, reason: str) -> dict:
    # Moves object to failed/ prefix and logs reason to Firestore + Cloud Logging
    ...
Why content-hash, not filename

Thousands of files migrated from a shared drive commonly include report.pdf, report_v2.pdf, and report_final.pdf as three copies of the same content — filename dedup misses this, hash dedup catches it.

5.4

Complexity classification

Not every PDF needs the expensive path. A cheap pre-check avoids paying for heavy processing on simple text documents.

def classify_complexity(pdf_bytes: bytes) -> str:
    import fitz
    doc = fitz.open(stream=pdf_bytes, filetype="pdf")
    has_tables_heuristic = False
    image_count = 0
    for page in doc:
        image_count += len(page.get_images(full=True))
        # crude table signal: multiple aligned horizontal lines (drawings)
        if len(page.get_drawings()) > 15:
            has_tables_heuristic = True
    if has_tables_heuristic or image_count > 3 or doc.page_count > 50:
        return "complex"
    return "standard"

standard → Document AI's default OCR processor (cheaper, faster). complex → Layout Parser (better table/structure fidelity, higher cost per page). This routing decision should be validated against real cost/quality data in Phase 1, not treated as final.

5.5

Text & table extraction

Bulk migration uses the Document AI batch API, not the synchronous one — thousands of documents through the sync API will hit rate limits and is the wrong tool for volume. Batch processing is async, handles large sets, and writes results back to GCS.

ingestion/extraction/batch_layout_parse.py 
from google.cloud import documentai_v1 as documentai

def submit_batch_extraction(
    input_prefix: str, output_prefix: str,
    project_id: str, location: str, processor_id: str,
) -> str:
    client = documentai.DocumentProcessorServiceClient()
    processor_name = client.processor_path(project_id, location, processor_id)

    input_config = documentai.BatchDocumentsInputConfig(
        gcs_prefix=documentai.GcsPrefix(gcs_uri_prefix=input_prefix)
    )
    output_config = documentai.DocumentOutputConfig(
        gcs_output_config=documentai.DocumentOutputConfig.GcsOutputConfig(
            gcs_uri=output_prefix
        )
    )
    request = documentai.BatchProcessRequest(
        name=processor_name,
        input_documents=input_config,
        document_output_config=output_config,
        process_options=documentai.ProcessOptions(
            layout_config=documentai.ProcessOptions.LayoutConfig(
                chunking_config=documentai.ProcessOptions.LayoutConfig.ChunkingConfig(
                    chunk_size=800, include_ancestor_headings=True
                )
            )
        ),
    )
    operation = client.batch_process_documents(request=request)
    return operation.operation.name  # long-running op — poll or use Cloud Function callback
Batch sizing constraint

Document AI batch requests cap at 50 documents (or 500 pages, whichever is smaller) per call in most processor quotas — confirm current limits for your processor/project before Phase 1, since these are quota-managed and change. For thousands of PDFs, the submission job must chunk the corpus into batches of that size and track each batch's long-running operation ID in Firestore, not submit all documents in one call.

Table output: Layout Parser returns tables as structured elements (rows/cells), not flattened text. Convert to markdown table syntax before writing to the sidecar — this is what preserves row/column meaning through to the embedding step, versus a flattened table reading as word soup.

def table_to_markdown(table_element) -> str:
    rows = table_element.body_rows + table_element.header_rows
    lines = []
    for i, row in enumerate(rows):
        cells = [cell.text.strip().replace("\n", " ") for cell in row.cells]
        lines.append("| " + " | ".join(cells) + " |")
        if i == len(table_element.header_rows) - 1:
            lines.append("|" + "---|" * len(cells))
    return "\n".join(lines)
5.6

Image extraction & description

Conditional

Only runs on documents flagged with image_count > 0 from Section 5.4, and only proceeds to production build if Phase 1 evidence justifies it.

ingestion/extraction/image_pipeline.py 
import fitz
import vertexai
from vertexai.generative_models import GenerativeModel, Part
from tenacity import retry, stop_after_attempt, wait_exponential

vertexai.init(project="PROJECT_ID", location="us-central1")
model = GenerativeModel("gemini-2.5-flash")

MIN_IMAGE_DIM = 100  # px — filters logos/icons/decorative dividers

def extract_images(pdf_bytes: bytes) -> list[dict]:
    doc = fitz.open(stream=pdf_bytes, filetype="pdf")
    results = []
    for page_num, page in enumerate(doc):
        page_text = page.get_text()[:500]
        for img in page.get_images(full=True):
            base = doc.extract_image(img[0])
            if base["width"] < MIN_IMAGE_DIM or base["height"] < MIN_IMAGE_DIM:
                continue  # skip decorative noise — real content only
            results.append({
                "page": page_num + 1,
                "image_bytes": base["image"],
                "mime": f"image/{base['ext']}",
                "context": page_text,
            })
    return results

@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=2))
def describe_image(image_bytes: bytes, mime: str, context: str) -> str:
    resp = model.generate_content([
        Part.from_data(image_bytes, mime_type=mime),
        "Describe this image factually for a knowledge base entry. If it is a "
        "chart, diagram, or screenshot, describe the data/structure/content shown "
        "concretely enough that someone could answer a question about it without "
        f"seeing the image. Surrounding page text: {context}",
    ])
    return resp.text
Cost control

At thousands of PDFs, unfiltered image extraction (including every logo and divider graphic) multiplies Gemini calls unnecessarily. The size filter above is a first pass; Phase 1 should sample actual extracted images to see what proportion are noise and tighten the filter accordingly.

Metadata assembly

def assemble_metadata(object_name: str, gcs_metadata: dict, doc_ai_result) -> dict:
    return {
        "document_name": object_name.split("/")[-1],
        "source": "pdf_corpus",
        "owner": gcs_metadata["owner"],

5.8

Consolidation & write-back

Text, table markdown, and image descriptions are merged into a single indexable content artifact per document — plain text with table blocks inline and an appended "Figures" section for image descriptions — written to gs://{bucket}/processed/{doc_id}.txt. This content file is referenced by URI from the manifest built in Section 5.9, not read directly by a bucket-wide glob.

def write_consolidated_content(doc_id: str, text: str, tables_md: list[str], image_descriptions: list[str], bucket_name: str) -> str:
    parts = [text]
    if tables_md:
        parts.append("\n\n## Tables\n\n" + "\n\n".join(tables_md))
    if image_descriptions:
        parts.append("\n\n## Figures\n\n" + "\n\n".join(image_descriptions))

    from google.cloud import storage
    blob = storage.Client().bucket(bucket_name).blob(f"processed/{doc_id}.txt")
    blob.upload_from_string("\n".join(parts), content_type="text/plain")
    return f"gs://{bucket_name}/processed/{doc_id}.txt"
5.9

Import to Vertex AI Search

Corrected from an earlier draft

data_schema="document" with a raw *.json glob does not work for this pipeline — that schema expects a specific structured Document proto per line, not a metadata sidecar. The correct schema for "content file + our own citation metadata" is custom, which pairs each content file with a JSONL manifest entry carrying structData and a content.uri pointer. Metadata is batched into manifest lines, not scattered as one small file per document.

Step 1 — build the manifest (one line per document, batched per import run):

ingestion/import/build_manifest.py 
import json
from google.cloud import storage

def build_manifest(documents: list[dict], bucket_name: str, manifest_name: str) -> str:
    """documents: list of {doc_id, content_uri, structData} dicts from 5.7/5.8"""
    lines = []
    for doc in documents:
        lines.append(json.dumps({
            "id": doc["doc_id"],
            "structData": doc["structData"],   # document_name, source, owner,
                                                # classification, last_updated, page_count
            "content": {
                "mimeType": "text/plain",
                "uri": doc["content_uri"],       # gs://.../processed/{doc_id}.txt
            },
        }))
    manifest_path = f"manifests/{manifest_name}.jsonl"
    storage.Client().bucket(bucket_name).blob(manifest_path).upload_from_string(
        "\n".join(lines), content_type="application/jsonl"
    )
    return f"gs://{bucket_name}/{manifest_path}"

Step 2 — import against the manifest:

from google.cloud import discoveryengine_v1 as discoveryengine

def trigger_import(project_id: str, location: str, data_store_id: str, manifest_uri: str):
    client = discoveryengine.DocumentServiceClient()
    parent = client.branch_path(
        project_id, location, data_store_id, "default_branch"
    )
    request = discoveryengine.ImportDocumentsRequest(
        parent=parent,
        gcs_source=discoveryengine.GcsSource(
            input_uris=[manifest_uri],   # the .jsonl manifest, not a *.json glob on content files
            data_schema="custom",
        ),
        reconciliation_mode=discoveryengine.ImportDocumentsRequest.ReconciliationMode.INCREMENTAL,
    )
    operation = client.import_documents(request=request)
    return operation.operation.name

INCREMENTAL mode adds/updates without wiping the existing index — this matters once the initial bulk load is done and the pipeline is running ongoing intake (Flow B). Bulk migration's first run can use FULL reconciliation once, deliberately, with sign-off — not by default.

5.10

Post-import verification

  • Poll the import operation until complete; log per-document success/failure from the operation response (partial failures are normal at volume — a handful of malformed documents shouldn't block the batch)
  • Run 3–5 known queries from the golden dataset (Section 9.2) against the data store immediately after each batch import completes, as a smoke test — catches a systemic problem (e.g. a schema mismatch) before it silently affects thousands of documents
  • Update Firestore status to indexed only after this check passes
5.11

Status tracking & retry

Every document's lifecycle lives in one Firestore document, keyed by content hash, so any stage can resume from where it failed rather than restarting the whole pipeline:

{content_hash}: {
  object_name, status: intake|validated|extracted|described|assembled|
                        importing|indexed|failed,
  failed_stage, failure_reason, retry_count,
  timestamps per stage
}

A Cloud Scheduler job runs hourly, queries for status=failed AND retry_count<3, and re-enqueues those documents at their failed stage. Documents exceeding 3 retries alert to the team (Cloud Monitoring alert on the Firestore query result) rather than retrying indefinitely.

5.12

Throughput & cost note for bulk migration

For "thousands" of documents: Document AI batch pricing is per-page, and the batch API has per-project quota on concurrent batch operations. Before Phase 1 execution, get current per-page pricing and concurrent-batch quota for the target project and use it to size how many days the bulk migration realistically takes — this is a scheduling input, not just a cost line.

Build gate

Section 5.6 (image extraction) is built only if Phase 1 evidence justifies it. If sampling shows few PDFs carry meaningful diagrams, that stage is deferred and the overall estimate drops by roughly 1.5 weeks.
