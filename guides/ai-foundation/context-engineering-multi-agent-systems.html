Context Engineering for Multi-Agent Systems

A practical guide to keeping context manageable as agent systems scale — strategies, real-world failure modes, and how teams are solving them (2026).

Why This Is a Problem

Context is a finite, expensive resource. Every LLM call pays a quadratic-ish attention cost as context grows, and empirically, model accuracy drops well before the window fills — a phenomenon Anthropic and others call “context rot.” Chroma’s research and Anthropic’s own engineering team have both shown that beyond roughly 50K tokens of relevant information, signal starts drowning in noise, and the classic “lost in the middle” effect kicks in: models get worse at recalling facts buried in a long context, even when the context window nominally supports millions of tokens.

In a single agent, this is already hard: you’re balancing system prompt, tool definitions, few-shot examples, conversation history, and retrieved data — all competing for the same token budget.

In a multi-agent system, the problem compounds in three specific ways:

  1. Multiplication — a 5-agent pipeline where each agent naively inherits 100K tokens of upstream context costs 5x what it should. Context routing that trims each agent down to only what it needs can cut this to a fraction of the naive cost.
  2. Drift — if a planner agent, a data agent, and a governance agent each work from slightly different snapshots of “the truth” (different ARR definitions, stale policy versions, inconsistent entity IDs), the system can look coordinated while quietly producing a wrong answer. The agents all completed their tasks; the context failed.
  3. Handoff loss — when Agent A hands off to Agent B, what actually transfers? Full transcript? A summary? A structured object? Get this wrong and you either blow the budget (full transcript) or lose critical detail (bad summary).

The rest of this doc covers the main strategies people use to manage this, with real challenges and how teams have actually solved them, then compares the options.

Option 1: Context Isolation (Sub-Agent Scoping)

The idea: Each agent gets its own private, narrow context window rather than inheriting the full conversation. A supervisor/orchestrator agent decomposes a task, and each sub-agent only sees the slice relevant to its job.

How it works in practice: This is the pattern behind Anthropic’s own multi-agent research system (described in their engineering blog on building it) — a lead agent breaks a research question into sub-questions, spins up sub-agents that each work in their own isolated context (their own tool calls, their own retrieved documents), and only the sub-agent’s final synthesized output — not its full working transcript — gets passed back to the lead agent. Google ADK follows the same shape: a root agent orchestrates specialized sub-agents (e.g., a “knowledge agent,” a “status agent,” a “ticketing agent”), each with its own tool set and instructions, and only structured results flow back up.

Real-world challenge: Anthropic’s own postmortems on this system noted that isolated sub-agents can duplicate work (two sub-agents independently researching the same sub-topic) or miss context that would have prevented redundant tool calls, because they can’t see what siblings are doing. The fix teams converge on is giving the orchestrator — not the sub-agents — responsibility for deduplication and for writing a short “here’s what’s already been covered” note into each new sub-agent’s initial context.

Where you’d use it: This maps directly onto your PLM support agent — the root ADK agent shouldn’t hand the full conversation to the ServiceNow tool-calling sub-agent; it should hand it a clean, scoped task (“create a ticket for X, category Y”) and get back a ticket number, not a transcript.

Option 2: Compaction / Rolling Summarization

The idea: Instead of keeping the full message history, periodically compress older turns into a summary and drop the raw messages, keeping only the summary plus recent turns in context.

How it works in practice: This is the core technique described in Anthropic’s “effective context engineering” writeup — when a conversation or task approaches the context limit, the system triggers a compaction step: an LLM call summarizes everything so far into a compact form (decisions made, open questions, key facts extracted), the old messages are evicted, and the agent continues from the summary. Claude Code does this for long coding sessions; long-horizon web/research agents do it every N tool calls rather than waiting for a hard limit.

Real-world challenge: Naive summarization loses precision — an agent handling a multi-step ServiceNow ticket lifecycle can’t afford to summarize away an exact ticket ID or a specific field value, only to hallucinate it back later. Teams solve this by splitting context into “summarizable narrative” (what happened, why) versus “structured facts” (IDs, statuses, entity references) that are pulled out into a small persistent state object and never summarized — only appended/updated. The summary handles narrative; the state object handles ground truth.

Where you’d use it: Your internal data agent, if it runs multi-turn analytical sessions (user asks a question, gets a partial answer, refines, asks again), is a good candidate — compact the exploratory back-and-forth but keep a running “facts established so far” block (table names queried, filters applied) untouched.

Option 3: Just-in-Time Retrieval Instead of Context Stuffing

The idea: Don’t pre-load a knowledge base into context. Instead, give the agent a retrieval tool and let it pull only the specific chunks it needs, when it needs them — RAG as a context-management technique, not just a knowledge-access technique.

How it works in practice: This is standard now across Vertex AI Vector Search, Gemini File Search, and most enterprise agent stacks — exactly the pattern you’re already using in AskLore and the PLM support agent (Confluence docs synced into a vector store rather than dumped into the prompt). The “just-in-time” refinement on top of basic RAG is having the agent do a cheap relevance pass first (e.g., a fast classifier or a lightweight retrieval step) before deciding whether a full retrieval-and-generation cycle is even needed — Self-RAG and FLARE-style approaches trigger retrieval only when the model’s confidence drops, rather than retrieving unconditionally on every turn.

Real-world challenge: Coding agent teams (Sourcegraph is a good public example) found that naive top-k vector retrieval on large, messy codebases pulls in a lot of near-relevant-but-wrong context — old commits, superseded patterns — which pollutes the agent’s reasoning worse than having less context at all. Their fix was layering retrieval: vector search + keyword search + structured/graph queries running in parallel, then merging and re-ranking before anything reaches the model, rather than trusting a single retrieval method.

Where you’d use it: This is directly relevant to your Confluence-backed PLM support agent — module-wise, domain-scoped retrieval (only search the “costing” domain’s docs if intent classification says it’s a costing question) avoids the cross-domain noise problem you’d get from one flat vector index across all modules.

Option 4: Structured External Memory (“Scratchpads” / Notes Files)

The idea: Instead of keeping working state in the conversation itself, the agent writes structured notes to an external store (files, key-value memory, a database) and reads back only what’s relevant, treating the context window as short-term working memory and the external store as long-term memory.

How it works in practice: Claude Code’s own memory/skills pattern and multi-agent frameworks like LangGraph’s persistent state stores both do this — a supervisor agent maintains a small structured “plan” or “task list” object outside the LLM context, updates it after each step, and only feeds the current relevant slice back into context on the next call. This is also how tools like Cursor and Claude Code avoid re-deriving “what have I already tried” every turn — it’s written down, not re-inferred from a long transcript.

Real-world challenge: The failure mode here is stale or conflicting memory — if two agents (or two runs) write to the same memory store with different assumptions, you get exactly the “data agent uses one ARR definition, governance agent uses another” problem enterprise context-engineering write-ups describe. The emerging fix in 2026 enterprise stacks is a shared context/metadata layer (sometimes marketed as a “context graph”) that all agents read from and write to under a single schema, with provenance tracked per fact, so an agent’s answer can be traced back to which source and which version of a definition it used.

Where you’d use it: Session memory for your production support agent (a stated v2/production requirement) is exactly this pattern — a per-user or per-ticket structured memory object, not a growing raw transcript.

Option 5: Orchestrator–Worker Context Routing

The idea: A dedicated orchestrator/router decides, per request, exactly which agents get invoked and exactly what slice of context each one receives — nothing is broadcast to every agent by default.

How it works in practice: This is the architecture pattern behind most production multi-agent frameworks now (Google ADK, LangGraph supervisor pattern, AutoGen). The router does lightweight intent classification first (cheap, fast, small context) and only then constructs a minimal, task-specific context payload for the agent(s) that actually need to run. Your own AskLore two-tier design — intent classifier + domain-scoped agents — is this pattern.

Real-world challenge: The 2026 enterprise literature on this (Deloitte/KPMG surveys cited in recent context-engineering papers) flags that as organizations add more specialized agents, routing logic itself becomes a maintenance burden — the router’s own “which agent handles what” knowledge needs the same context discipline as everything else, or you get misrouted requests. Teams solve this by keeping routing rules in a small, versioned, testable config/spec (sometimes called “specification engineering”) rather than letting routing logic live implicitly in a growing system prompt.

Where you’d use it: This is your existing architecture on both AskLore and the internal data agent (routing between the unstructured RAG path and the structured BigQuery/RDBMS path based on query type) — the main risk to watch as you add more sub-agents is exactly the “routing logic sprawl” problem above.

Option 6: Aggressive Tool-Result and History Pruning

The idea: Don’t keep full tool outputs in context indefinitely — truncate, filter, or discard tool results once their information has been used or superseded.

How it works in practice: A ServiceNow ticket search that returns 40 tickets doesn’t need all 40 tickets’ full JSON sitting in context for the rest of the session — the agent extracts what it needs (ticket numbers, statuses) into a compact form and the raw tool output is dropped. Long-running agent frameworks apply a “most recent N tool calls kept in full, older ones summarized or dropped” sliding-window policy by default.

Real-world challenge: Over-aggressive pruning causes agents to re-call the same tool because they “forgot” they already had the answer — a real, commonly reported failure mode in long-horizon agents. The fix is pairing pruning with Option 4 (structured memory): extract the durable fact from a tool result before discarding the raw result.

Where you’d use it: Directly applicable to your ServiceNow ticket lifecycle tool calls (create/update/list/search) — keep the ticket IDs and statuses in structured state, discard the raw API payloads.

Comparison Table

Strategy Solves Cost to implement Main failure mode if done wrong Best fit
1. Sub-agent isolation Context multiplication across agents Medium — needs orchestrator design Duplicated work between siblings Any multi-agent system with parallelizable sub-tasks
2. Compaction/summarization Long conversation history bloat Medium — extra LLM calls, summary quality risk Losing precise facts (IDs, values) in the summary Long multi-turn sessions (support chat, research)
3. Just-in-time retrieval (RAG) Pre-loading entire knowledge bases Medium-High — retrieval infra, ranking Irrelevant/stale chunks polluting reasoning Knowledge-heavy agents (your Confluence/PLM case)
4. Structured external memory Stale/inconsistent state across turns or agents High — needs schema, storage, provenance Conflicting writes from different agents Session memory, cross-agent shared facts
5. Orchestrator-worker routing Sending full context to every agent by default Medium — router + intent classification Routing logic itself becomes unmanageable Systems with 3+ specialized agents (AskLore-style)
6. Tool-result pruning Context growth from verbose tool outputs Low — straightforward filtering Agent re-calls tools it “forgot” it already used Any agent with chatty tools (search, ticketing APIs)

None of these are mutually exclusive — production systems (including Anthropic’s own research agent and most enterprise ADK/LangGraph deployments) combine all six: an orchestrator (5) routes to isolated sub-agents (1), each of which retrieves just-in-time (3), prunes its own tool chatter (6), and periodically compacts its working history (2), while durable facts get written to shared structured memory (4) rather than living in any single agent’s transcript.

The Underlying Failure Pattern to Watch For

Across almost every real-world writeup on this (Anthropic’s, the enterprise context-graph vendors, the academic surveys), the actual root-cause failure isn’t “context window too small” — it’s inconsistent ground truth across agents: two agents silently operating on different versions of the same fact. The fix is architectural, not just a token-budget trick: a single shared, versioned source of truth (Option 4, done well) that every agent reads from, with enough provenance tracking that a wrong answer can be traced back to which agent used which stale fact.

For a system like your PLM support agent — where correctness (ticket routing, SOX-compliant summaries, status accuracy) matters more than cleverness — that’s the piece worth over-investing in relative to the others.
