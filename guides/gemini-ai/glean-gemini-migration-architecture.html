Glean → Gemini Enterprise Migration

Architecture overview and open questions for the MCP-based bridging approach — internal working notes

1. Migration goal & approach

The organization is moving its primary enterprise search from Glean to Google Gemini Enterprise. Users today search across sources like SharePoint, Outlook, and other systems through Glean's unified knowledge graph. Rather than a hard cutover, the plan is a phased migration: keep Glean active as a bridge via a custom MCP (Model Context Protocol) connector inside Gemini Enterprise, while native Gemini Enterprise connectors are progressively built out for each source.

3. Key configuration facts confirmed

ItemDetail
MCP registration path Glean is added as a custom MCP server data store inside the Gemini Enterprise console (Data stores → Create data store → Custom MCP Server), pointed at Glean's MCP endpoint (backend domain + /mcp/default).
Endpoint count Just one URL is registered on your side. Glean's multi-region HA and failover live entirely behind that single endpoint — there's no dual-endpoint failover config for you to manage.
Transport Gemini Enterprise's custom MCP connector only supports StreamableHTTP — the older SSE transport is not supported.
Org policy prerequisite Custom MCP data stores are blocked by default via an org policy constraint. An Org Policy Administrator must override it before setup.
Permissions model Every MCP call runs under the end user's own identity — Glean never elevates privileges. Results stay scoped to what that user could already see in source systems.
Routing instructions Set per-connector, in the MCP Server Description field on that specific data store's configuration (not a global setting). This is where you'd write guidance like "only use this source for content not yet natively connected."

4. Open questions to validate

Open — validate with Google Cloud account team How does Gemini Enterprise behave if the Glean MCP data store is unreachable?

Not publicly documented. Best-guess inference (not confirmed): since each data store is a separate connector feeding into blended search, an outage on the Glean side likely means that one data store returns no results/times out while other native connectors (SharePoint, Outlook, etc.) keep working — i.e. partial degradation rather than a full search failure. Whether the end user sees an explicit error for that one source, or it silently drops out, is unconfirmed and should be tested directly or asked of Google.

Open — validate with Glean account team Does Glean's "multi-region HA" mean true multi-region, or multi-AZ within one region?

Glean states MCP endpoints inherit the same platform guarantees as the rest of Glean — including multi-region HA and regional data residency (AMER/EMEA/APAC) — backed by a 99.9% uptime SLA at the premium support tier. What's not clear from public docs is whether "multi-region HA" for your specific tenant/plan actually spans multiple regions or just availability zones within a single region. This matters directly for a Germany-based deployment and its data residency requirements.

Resolved / working approach How to avoid duplicate results when a source is connected both natively and via Glean MCP?

Gemini Enterprise has no platform-level failover switch ("try native, only fall back to MCP on failure"). What it offers is intent-based routing via the MCP Server Description field. The working approach: write explicit instructions in that field telling the orchestrator to only invoke the Glean MCP tool for content not yet available through a native connector, and manually retire the overlap as each source is migrated natively. This is a soft, LLM-followed instruction, not a hard platform rule — worth testing and refining once live.

5. Scale considerations (100,000+ users)

No public source publishes one blanket concurrency ceiling for Glean's MCP layer. What's documented is tiered: agent-run initiation is capped around 30 queries/minute, and individual native connectors (e.g. Confluence) default to about 2 queries/second per user. There's no single number that maps cleanly to "100,000 concurrent users through one MCP bridge" — at this scale, deployment-tier capacity is a negotiated conversation with Glean's account team, not something derivable from public docs alone.
